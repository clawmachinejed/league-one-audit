# Account authentication foundation

This integration is dormant by default. It adds account authentication and application admission for the existing league library. It does not change public league access, provider account ownership, collection admission, or league-family authorization. A Sleeper username is not authentication evidence.

## Maintained integration and exact release

The app uses `@neondatabase/auth@0.5.0-beta`, the published version checked on September 22, 2026. Its npm tarball matched the registry integrity `sha512-s/CHBVlX7hzm1iJJpDKKDiv5zIXQqYxeGJC/3oRjs1mjY35Hzg+qM7rj/h6DVY3qrvl5jgILcrOnLtyYq/N80A==`. The package declares Next.js >=16 and React >=18 peers. Type checking against this application's Next 16.3.3, React 19.2.8 and Node 24 succeeds. This is SDK/type compatibility evidence, not a live managed-auth qualification.

Use `createNeonAuth` from `@neondatabase/auth/next/server` on the server and `createAuthClient` from `@neondatabase/auth/next` on the client. Credentials, cookie issuance, password verification and session validation remain with the maintained SDK/service. Do not add a second credential or session implementation. The managed service and SDK version numbers are different: Neon's overview currently names Better Auth 1.4.18 for the service, while this SDK depends on Better Auth 1.6.23. Generic current Better Auth configuration options are not proof that the managed service exposes them. The managed service is described as generally available while the npm SDK retains its beta version. [Managed overview](https://neon.com/docs/auth/overview), [supported feature roadmap](https://neon.com/docs/auth/roadmap).

### Guarded dependency-graph workaround

The published SDK pins Neon UI 0.3.0-beta, which pins Davey UI 3.4.0. Davey UI's API-key range `^1.5.6` selected API-key 1.7.5, whose auth/core requirements conflicted with the SDK's exact Better Auth 1.6.23. The workspace pins only this dependency edge to API-key 1.6.23, within the UI's original range. API-key still needs better-call 1.3.7 while its UI parent requires 2.0.2, and the floating core peers otherwise select 1.7.5. [Neon UI metadata](https://registry.npmjs.org/@neondatabase/auth-ui/0.3.0-beta), [Davey UI metadata](https://registry.npmjs.org/@daveyplate/better-auth-ui/3.4.0), [API-key metadata](https://registry.npmjs.org/@better-auth/api-key/1.6.23).

The root `.pnpmfile.mjs` therefore supplies compatible package-local dependencies for three edges: API-key 1.6.23's core 1.6.23 and better-call 1.3.7, plus passkey 1.6.23's core 1.6.23. It first asserts the exact published peer strings and absence of an existing ordinary dependency, and throws on unexpected metadata. It changes only resolution metadata for these exact versions; it does not change package JavaScript, SDK/authentication behavior, or either UI's own better-call dependency. No peer warnings are suppressed. Ordinary packageExtensions and alias overrides did not replace the conflicting peer bindings in the tested pnpm 11.19.0 graph; the explicit hook performs the required move. [pnpm readPackage hook](https://pnpm.io/pnpmfile#hooksreadpackagepkg-context-pkg--promisepkg).

`pnpm verify:dependencies` runs both `pnpm peers check` and `apps/site/scripts/verify-account-auth-dependencies.mjs`. The latter verifies actual Node resolution against the original on-disk published peer declarations and asserts SDK, UI and plugin versions; it also checks the hook's exact-version and metadata guards. This is necessary because the moved peer edges are ordinary dependencies in pnpm's resolved graph. Root `pnpm verify` starts with this check, and `pnpm verify:full` invokes `verify` before browser and isolated database checks.

The isolated probe passed peer validation, a frozen installation with lifecycle scripts disabled, and original-peer module-resolution checks. Treat this as a beta SDK graph maintenance requirement, not a security assessment. Reassess it on every SDK/UI/plugin upgrade. Remove the hook and edge pin when an upstream published graph passes the same original-peer checks without them; keep all checks active while the workaround exists. Never replace it with a global better-call downgrade or ignored peer errors.

## Required server configuration

| Variable | Meaning |
| --- | --- |
| `ACCOUNTS_ENABLED` | Must equal `true`; otherwise no account auth request is sent. |
| `NEON_AUTH_BASE_URL` | Exact HTTPS managed branch endpoint ending `/auth`; also the normalized trusted identity issuer. |
| `NEON_AUTH_COOKIE_SECRET` | Independent random secret, at least 32 characters; keep in the deployment secret store. |
| `ACCOUNTS_INVITED_EMAILS` | Comma/newline separated pilot email allowlist; required, server only. |
| `ACCOUNTS_APP_ORIGIN` | Exact app origin for auth POST requests. HTTPS is required except localhost in a local nonproduction process without `VERCEL_ENV`. |

Vercel Preview is always disabled even if all variables are present. Do not inject production auth credentials to make a preview work. The private database has its own independent guard; auth availability alone does not make account persistence available.

The issuer comes from server configuration, never incoming Host/Origin or a client-selected identity. Preserve the production issuer/subject mapping through ordinary deploys. A different Neon auth branch is a different issuer; any migration of real identities across branches needs an explicit mapping/recovery plan. Use a distinct cookie secret for each isolated environment and retain the production secret securely for recovery. Do not share cookies across subdomains.

## Private admission and authoritative sessions

`getAccountPrincipal()` calls the SDK for a fresh session, checks session expiry and subject consistency, requires `emailVerified === true`, and checks the pilot allowlist before returning only issuer, subject and display name. No email is returned to the domain layer or used as the persistent user key. Uninvited or unverified users cannot provision an application account through this helper. Missing sessions return null; unavailable configuration/provider responses and failed admission have separate safe error types.

There is a release-specific cache issue to preserve in regression coverage. The SDK server implementation bypasses its signed five-minute session cache only for the serialized string `query.disableCookieCache: 'true'`. The app deliberately passes that string. It compiles against the installed declarations without a type assertion. The test first proves the SDK accepts a synthetic signed cache, then verifies that the app still contacts the upstream service and rejects a revoked session. `sessionDataTtl: 0` is not an alternative: the SDK rejects nonpositive TTLs. This is an application use of the SDK's existing bypass, not custom session validation. [Maintained server implementation](https://github.com/neondatabase/neon-js/blob/main/packages/auth/src/server/client-factory.ts).

The SDK's actual cookie default is `lax` despite a reference table describing `strict`. The app pins `sameSite: 'lax'`, preserves Secure/HttpOnly handling, and uses exact configured Origin checks plus the managed service's trusted-origin checks. The application proxy permits only the email account lifecycle endpoint set, rejects other methods/routes, accepts valid UTF-8 JSON objects on POSTs, and limits actual bodies to 16 KiB even when Content-Length is absent or incorrect. Responses are private/no-store. Public league routes do not get a blanket auth proxy/middleware.

Before forwarding signup to the service, the proxy requires its email to match the server invite list after trimming and case normalization. If `callbackURL` or `redirectTo` is present in a POST body, it must be an absolute URL with the exact configured application origin and `/sign-in` path, without credentials, query parameters or a fragment. These two fields are rejected in the request query because the SDK forwards search parameters unchanged. Other recovery parameters, such as a reset token, remain the maintained service's responsibility. The UI uses the approved absolute `/sign-in` callback for verification and recovery.

Password recovery stays on `/sign-in` and calls the maintained `requestPasswordReset` and `resetPassword` SDK methods. A callback token is opaque, held only in component memory, and removed from the URL and router history. The initial document has `Referrer-Policy: no-referrer` and private/no-store caching before hydration; this does not claim the initial token-bearing URL never reaches the hosting provider. Reset requests give a generic response without exposing whether an email has an account. Password confirmation, invalid/expired links and return to ordinary sign-in are covered by synthetic browser tests; actual mail delivery, callback shape, single use and other-session revocation remain live qualification gates. The installed Better Auth implementation only revokes existing sessions on reset when the managed `emailAndPassword.revokeSessionsOnPasswordReset` policy is enabled. A UI refresh event does not revoke sessions: prove old cookies fail on another device before activation. A new callback route requires an explicit allowlist change.

The proxy does not expose `delete-user`. Managed identity deletion and local identity tombstones, session revocation and application-data handling require a coordinated operator procedure; a vendor deletion endpoint is not that procedure. The route's 30-second platform execution limit bounds the deployed invocation, not an asserted upstream cancellation mechanism.

The pinned browser SDK throws its declared authentication errors before returning Better Auth's ordinary error envelope. `accountAuthRequest` uses the SDK's own `isAuthError` classifier to route those failures into the UI's credentials/invalid-link handling while preserving actual transport failures as temporary outages. Regression tests invoke the installed client with synthetic fetch responses; they do not substitute a fake SDK or validate live managed-service behavior.

## Hosted registration is a separate control

This code enforces **invite-gated application admission** and rejects uninvited signup through the application proxy before provider account creation or email delivery. It does not promise that the hosted auth service cannot create an uninvited identity. Hiding a signup form or narrowing the app proxy does not close the direct managed endpoint. The proxy signup gate is not a service-wide mail rate limiter, and verification/recovery delivery still needs managed-service controls and testing.

Neon's current email-password configuration API exposes `disable_sign_up`, `require_email_verification`, OTP/link method and verification-send settings. Magic Link has a separate signup flag. However, the authentication-flow guide still says signup restrictions are coming soon. Verify the chosen branch's configuration and direct endpoint behavior before describing enrollment as closed. For this pilot, enable only email/password with required verification; keep social login, passwordless signup and unused plugins disabled. Do not temporarily open registration to onboard individual users. If using precreated identities, independently prove the supported invitation/recovery path. [Email-password configuration API](https://neon.com/docs/reference/api/auth/update-neon-auth-email-and-password-config), [Magic Link configuration](https://neon.com/docs/auth/guides/plugins/magic-link), [authentication flow](https://neon.com/docs/auth/authentication-flow).

## Qualification gates before account activation

1. **Service identity and activation.** Confirm exact Neon project/branch/database and the app origin; enabling Auth creates service configuration and `neon_auth` schema. It is a service/security mutation, not read-only setup. Complete applicable provider approval requirements before performing it. Keep the recovery branch and production untouched during qualification.
2. **Synthetic isolation.** Start from an isolated branch without production identities, enable/configure auth there, use a unique secret, and allow only its explicit test origin. Branching copies users, sessions, signing keys and OAuth configuration; branch separation does not mean a child contains no sensitive data. Prove that credentials/cookies from another environment cannot authorize private app operations. Never use real-user credentials for synthetic lifecycle tests. [Auth branching](https://neon.com/docs/auth/branching-authentication), [branch service management API](https://neon.com/docs/auth/guides/manage-auth-api).
3. **Verified enrollment.** Prove successful signup/sign-in, required verification, resend, wrong/expired/reused code rejection, missing session, uninvited verified identity denial, duplicate signup, and direct alternate signup-path denial. Provider-managed OTPs are generated and sent by Neon; do not retrieve or synthesize real verification codes. [Verification guide](https://neon.com/docs/auth/guides/email-verification), [Email OTP](https://neon.com/docs/auth/guides/plugins/email-otp).
4. **Lifecycle.** Prove password recovery, current-session logout, other-device revocation, user ban/delete and stale-cookie rejection. The generic SDK endpoint is not proof that a managed feature is enabled. Published SDK types require `revokeSession({ token })`, despite a Neon reference example using `sessionId`. `changePassword` supports `revokeOtherSessions: true`; `requestPasswordReset`/`resetPassword` are the Better Auth APIs, not the Supabase-style `resetPasswordForEmail`. Confirm managed deletion verification and the separate application-data deletion process; never claim one vendor delete automatically cleans custom tables. Admin plugin calls require an authenticated admin session; do not add a Neon management API key to the application runtime. [User management](https://neon.com/docs/auth/guides/user-management), [password recovery](https://neon.com/docs/auth/guides/password-reset), [admin sessions](https://neon.com/docs/auth/guides/plugins/admin).
5. **Transport and browser behavior.** Test missing/foreign Origin, callback allowlisting, HttpOnly/Secure/SameSite, expiry, malformed provider responses, outages and latency. The pinned server SDK discards `fetchOptions` and does not expose an upstream AbortSignal/timeout hook; this adapter does not pretend to cancel through an uncancelled Promise.race. Confirm an acceptable platform execution limit or a maintained SDK cancellation path before live activation. Request body streaming is bounded by bytes, not a claimed network deadline.
6. **Production delivery and costs.** Configure an application-owned SMTP provider, production trusted origin(s), required verification and application name; turn off localhost on production. Shared SMTP is for development and has limits. Current plans list up to 1M auth MAU on Launch/Scale and 60,000 on Free; database compute/storage/branch usage and the mail provider can still cost money. Confirm actual account plan, limits and service costs before changing them. [Production checklist](https://neon.com/docs/auth/production-checklist), [current Neon plans](https://neon.com/docs/introduction/plans).

Account linking is deliberately outside the pilot. Generic Better Auth enables linking by default, including some verified-email OAuth matching; the current Neon material does not establish which linking policy controls are exposed on this branch. Do not infer a league-provider connection or ownership claim from an auth email match. Prove and document the managed policy before adding social identities. [Better Auth account linking](https://www.better-auth.com/docs/concepts/users-accounts#account-linking).

Local mocked tests qualify the adapter's admission, pre-provider signup invite check, origin, callback destinations, body, denied deletion route, feature flag and cache-bypass behavior. They do not qualify Neon's live SMTP, direct hosted signup controls, service-side revocation, recovery, cross-branch token rejection, or deletion. No real auth accounts, provider configuration or production database changes are performed by these tests.
