# First-slice quality decisions and operating evidence

Design revision: `first-slice-design-v1`. Application baseline: `87da4d0cb909ee280e125e73ad10e1c3dbd7cd9f`. This is a selected engineering design for the bounded internal identification → current teams → authorized stored roster path. Its decisions use the approved behavior in the [handoff](evidence/backend-workspace-handoff.md); they are not new product approvals or deployed settings. Exact requirements and verification oracles are in [the requirement ledger](design-requirements.json), relations/protocols in [the relational design](relational-design.md), and trust/state models in [the behavior/security design](behavior-security-design.md).

## Method and concern coverage

This analysis applies SEI's scenario structure and architecture tradeoff method: derive drivers, generate and consolidate scenarios, prioritize them, identify approaches, analyze consequences, then independently challenge the result. It is a tailored engineering evaluation using the actual approved brief, not a claim that a facilitated stakeholder QAW/ATAM or stakeholder vote occurred. [SEI QAW](https://www.sei.cmu.edu/library/quality-attribute-workshop-collection/) and [SEI ATAM](https://www.sei.cmu.edu/library/atam-method-for-architecture-evaluation/) are the method sources.

| Driver | Concern represented | Derived evaluation priority and rationale |
| --- | --- | --- |
| QD01 | Manager/co-manager sees only presently authorized information; L1 login is independent | P0: access correctness and isolation override availability of the affected league read |
| QD02 | Official facts, identities, season selection and evidence remain truthful | P0: no invented ownership, disappearance, freshness, results or cross-league identity |
| QD03 | Operator can recover from expiry, partial source data and process failure | P0 for safe recovery and durable work; P1 for convenience/latency without an approved SLO |
| QD04 | Shared infrastructure supports multiple independent managers | P1: reuse one compatible acquisition/normalization/publication path; separate user decisions |
| QD05 | Maintainer can evolve policy and adapters without corrupting existing readers/history | P1: explicit version binding, reversible compatibility and bounded privilege adapters |
| QD06 | Existing leagues and worker workloads continue without unapproved operational changes | P0 preservation; scale throughput, score-delay percentiles and cost optimization are later empirical targets |

P0 means a violated invariant blocks qualification. P1 means the selected implementation must satisfy the stated functional outcome, with performance evidence evaluated before activation. These are engineering priorities derived from the brief, not invented stakeholder voting results. All six drivers have scenarios below. Closely related source errors are consolidated into QA08; expiry recovery is separated from genuine loss/regain because D04 remains unresolved. The later 500-league objective is explicitly QA11 rather than silently being treated as a first-slice performance pass.

| AD01 | Sequential final rechecks; one database snapshot ignoring auth; global Serializable; ordered locks spanning separate restricted auth/account owners | Ordered locks and one final domain evaluation. ## Operating evidence contract

This selects required evidence and action semantics now. It does not install logging, alert schedules or production retention rules. Reuse existing account HTTP safe error handling, `app_identity_audit_events`, administration maintenance logging, projection logger conventions and durable job/acceptance state. A separate service, collector, telemetry account or new credential is not required.

### OE-1 — Minimal diagnostic envelope

The target new event is server-only. Serialize an allowlisted object with `schemaVersion:'membership-read-events-v1'`, `event` (one of the rows below), `occurredAt` (trusted UTC event instant), `correlationId` (server-generated UUID), `outcome` (event-specific enum below), `reason` (fixed enum), `policyVersion` (`sleeper-membership-access-v1` or null before evaluation), `bindingRevision` (positive canonical decimal string or null), and `durationMs` (nonnegative safe integer or null). Optional fields are only `count`, `oldestAgeSeconds`, `authorityGeneration`, `committed` and `suppressedProtectedFieldCount`. Counts and ages are integers in 0..9007199254740991; duration uses the same domain. `authorityGeneration` is a positive canonical decimal string for PostgreSQL BIGINT in 1..9223372036854775807, never a JavaScript number; `bindingRevision` uses that same domain. `committed` is a boolean. Optional fields cannot be null; omit when inapplicable. Null in required nullable fields means not evaluated or not applicable, never zero evidence age. No arbitrary metadata/message/error property is permitted. Values are internal and never added to denied/indeterminate DTOs.

`reason` is selected from: `ok`, `membership_unknown`, `membership_removed`, `membership_expired`, `association_ended`, `authority_revoked`, `dependency_changed`, `authority_unavailable`, `scope_mismatch`, `capture_unqualified`, `lease_lost`, `transaction_failed`, `deadline`, `protected_shape_rejected`, `evidence_sink_unavailable`. Unexpected driver details become `transaction_failed`; no SQLSTATE/message/connection details escape into routine logs. Event-specific outcome/reason combinations are checked by a serializer. Existing broader worker logs are not silently rewritten by this design.

| Event | Emit boundary and source of truth | Observer / operational action |
| --- | --- | --- |
| `access_decision` | After completed final decision, once per internal request; allow/deny/indeterminate with safe reason, evaluation policy/binding and duration | Account operator: distinguish expected expiry/removal from authority failures; never use an event as a grant |
| `dependency_rejected` | When final captured state cannot satisfy current coherent dependencies; one per discarded request, not one per row | Data/security operator: inspect safe correlation against protected audit; no automatic weakening/retry |
| `protected_shape_rejected` | Before any bytes are emitted if deny/indeterminate has extra keys; suppress result and record count only | Security/release owner: any occurrence blocks qualification and requires investigation before activation; no capture of the forbidden values |
| `revalidation_intent` | Only after durable intent commit/known idempotent existing intent; `committed:true`. On failed commit, emit failure with false and do not claim work queued | Existing worker/account operator: persistent job row is authority. Resume through existing job reservation, not event replay |
| `revalidation_backlog` | At an existing authorized operational inspection, compute pending count and oldest age from existing work/checkpoint records; no browser-triggered collection | Operator: inspect expired eligible-demand work, lease failures and provider availability. This adds no cron or monitoring frequency |
| `membership_evidence` | After acceptance commit or rejection; record qualified/unqualified outcome, safe authority generation and reason only | Existing administration operator: reconcile evidence acceptance with work intent; content/ref lookup stays in restricted source records |
| `evidence_sink_unavailable` | Increment one process-local saturating failure counter (0..9007199254740991); retain no event, correlation, time or payload. Reset on process restart. Never emit recursively through a failing sink. On the next successful ordinary emission, emit at most one summary with count and reset only after success | Operator: the fallback is best effort and can be lost on restart; restore evidence capture and verify the sink. It does not prove durable observation during an outage or alter authorization/audit outcomes |

The serializer accepts exactly the following outcome/reason/optional-field combinations. Any other combination is rejected. A missing diagnostic event never changes the domain result.

| Event | Outcome and reason | Optional-field contract |
| --- | --- | --- |
| `access_decision` | `allow`/`ok`; `deny` with `membership_removed`, `membership_expired`, `association_ended`, `authority_revoked`; or `indeterminate` with `membership_unknown`, `dependency_changed`, `authority_unavailable`, `scope_mismatch`, `capture_unqualified`, `transaction_failed`, `deadline` | None |
| `dependency_rejected` | `indeterminate` with `dependency_changed`, `authority_unavailable`, `scope_mismatch`, `transaction_failed`, `deadline` | None |
| `protected_shape_rejected` | `suppressed`/`protected_shape_rejected` | Required `suppressedProtectedFieldCount` > 0; no other optional fields |
| `revalidation_intent` | `committed`/`ok` with required `committed:true`; or `failed` with `lease_lost`, `transaction_failed`, `deadline` and required `committed:false` | Only `committed`; false means commit was not proved, including uncertainty, not proof of absence |
| `revalidation_backlog` | `observed`/`ok` | Required `count`; required `oldestAgeSeconds` only if count > 0; omit age for empty backlog; no other optional fields |
| `membership_evidence` | `accepted`/`ok` with required `authorityGeneration`; or `rejected` with `scope_mismatch`, `capture_unqualified`, `lease_lost`, `transaction_failed`, `dependency_changed` and no generation | Only the specified generation; rejected events never invent an accepted generation |
| `evidence_sink_unavailable` | `failed`/`evidence_sink_unavailable` | Required `count` > 0; no other optional fields; emitted only after sink recovers |

The failure counter is an uncorrelated aggregate with process lifetime bounded by restart and no persistence; successful summaries use the same seven-day maximum as other diagnostics. This fallback is deliberately not a separate health service or a promise of outage observability. G7 must prove the existing operational inspection can detect sink failure; otherwise activation remains blocked.

### OE-2 — Retention, privacy and durability

Existing immutable identity audit rows remain unchanged with their existing operator-only access and deletion prohibition. Source acceptance and necessary authorization/removal receipts follow their explicit relational history and dependency rules; they must not be pruned while referenced. Neither rule chooses D05's last-follower retention behavior.

New diagnostic envelopes have a **seven-day maximum retention** as an engineering minimization ceiling, not an extension of existing retention. Use the existing host sink only if its actual access and deletion/expiry configuration can enforce the ceiling, and keep shorter existing retention where applicable. Prove that condition at G7; otherwise withhold target activation until a compatible existing sink configuration is reviewed. Do not add a paid external sink or change production configuration in this task. Aggregate operating counts may be computed from retained job/evidence state; this design creates no historical analytics warehouse or longer retention exception. Qualification evidence uses synthetic fixtures and sanitized receipts, retained with release evidence under repository rules.

Correlations can link to operator-only audit records, so they are treated as restricted diagnostic information even without names. No user-facing endpoint exposes the event stream, cross-actor counts or another account's conflict identity. Log failure never turns a deny into an allow. A required transactional identity-audit or pending-work write failure rolls the mutation back; a nontransactional diagnostic sink failure cannot undo a completed valid decision and is separately observable.

### OE-3 — Concrete operating qualification and response

| ID | Fixture/procedure | Exact oracle / evidence |
| --- | --- | --- |
| OE-T01 | Exercise each event, inject extra raw error, email, cookie, provider ID and unexpected metadata fields into event input | Serializer rejects or removes every undeclared field; no sensitive sentinel appears in captured sink output; enum/null/domain checks pass |
| OE-T02 | Force final check failure after a roster is composed; instrument actual response byte serialization | Only status/reason DTO or safe transport failure appears; protected-shape detector emits count without values; zero roster/league/team/source keys |
| OE-T03 | Stop process at intent-before-commit, commit-before-ack and failed-diagnostic-emission boundaries | Persistent job/acceptance state, not logs, proves exactly one queued intent after commit; none before; replay is idempotent |
| OE-T04 | Queue recovery under expired membership, lease another job, inject provider failure and later positive evidence | Pending count/oldest age reflect real records; expiry remains T+3600 until qualifying evidence; normal worker can recover without an allow read |
| OE-T05 | Make diagnostic logger throw/unavailable on deny and allow; make mandatory mutation audit fail separately | Logging never authorizes; valid completed read outcome stays correct; audit-failed mutation rolls back; no recursive logging failure loop |
| OE-T06 | Inspect actual restricted operator/sink permissions and expiration using synthetic correlated events before activation | No browser/account access; configured maximum retention ≤ seven days and observed expiry, or target activation remains blocked; no provider content in sink |

Any demonstrated unauthorized payload, orphan accepted state without required work, unfenced writer, expiry extension or cross-actor result is a **stop condition at the first occurrence**, independent of a rate threshold. Routine denial/removal/expiry alone is not an incident. Evidence of unrecoverable queued work, repeated authority failures or inability to observe required outcomes triggers operator diagnosis and keeps activation blocked until explained. This design defines no new live alert cadence, paging contract or workload SLO; those must be qualified against actual operation rather than fabricated here.

## Verification and transition plan

The requirement ledger defines independent fixtures and observable oracles before executable work. Verification asks whether each obligation holds; validation uses manager/co-manager and operator walkthroughs to check that the approved intended outcome is represented. This separation follows the [NASA verification/validation matrix guidance](https://www.nasa.gov/reference/system-engineering-handbook-appendix/).

1. Freeze and review the design revision, requirement/invariant coverage, relation/constraint mapping, privilege changes and complete writer lock inventory. Author fixtures before composing target service changes. Preserve this review's design evidence independently of later runtime results.
2. Implement through existing owners in an isolated worktree: exact validators and pure policies; additive persistence functions/constraints/role manifests; then shared service composition. Existing routes and production behavior stay on their current path until separately authorized cutover. Do not modify applied migration history.
3. Verify pure/domain behavior with controlled clocks and source fixtures, then qualify real SQL/roles/locks/crashes through the existing disposable harness only under its exact authorization, identity, sentinel, TLS, role and denylist guards. Record full source SHA, fixture version, case IDs, actual result and cleanup receipt. A mocked database cannot close concurrency or RLS proof.
4. For migration rehearsal, measure active exclusivity conflicts, annual alias/key conflicts, missing lookup provenance and unsupported old rows; abort on unresolved conflicts. Compute pre/post counts and immutable-content hashes. New admission/current-selection rows require qualified evidence; never backfill an allow or lookup receipt from a display label or old preference. Rehearse interrupted backfill and idempotent resume on disposable synthetic data.
5. Preserve additive schemas and old reader compatibility. Before enabling the new path, verify new all-mutator fences, privileges and job atomicity together; partial enforcement is not an acceptable cutover. On failure disable the new internal entry/configuration binding, retain receipts and use a compatible reader only when its authorization remains valid. Never roll back by deleting evidence, weakening denial, selecting a stale policy or rewriting frozen scoring data. A destructive schema rollback is not authorized.
6. Before any public activation, resolve D03 and affected D04/D05 behavior, qualify optional-data/unknown-source UX, establish operator and safe sink access, and complete source/capacity measurements appropriate to the activation scope. Repeat main/GitHub/Vercel/canonical binding and production ownership checks; respect ordinary PR/protection/preview/full-check requirements. Merge/deploy only with release authorization; verify exact production SHA and both League One/Two afterward.

No production or disposable database was accessed for this design. Runtime, live source completeness, installed catalog, actual throughput, sink retention and user journey execution are later evidence, not implied by this document's selected decisions.
