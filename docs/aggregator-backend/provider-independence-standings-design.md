# First slice design: canonical official standings

Version 1.0 — October 21, 2026. Phase 1 design only. No application, SQL migration, fixture, test, database or provider execution is authorized by this document. CP28 and its original worktree/artifacts remain frozen.

## Requirement and source boundary

Implement one complete standings path in a later authorized phase: registered source identity → provider verification → common acceptance/materialization → stored read. A deliberately different isolated adapter must supply standalone standings without inventing a Sleeper roster capture. Existing Sleeper values, source history and legacy reads remain valid. This slice addresses F01/F03/F04/F06 and its scoped F02 identity needs; it does not close player links, all eight families, or operational checkpoints.

The shared rules and identity prerequisites are defined in [Phase 1 shared design](provider-independence-phase1-design.md). This document specifies the standings payload, evidence route, affected objects, privilege boundary and first proof cases. The [remediation plan](provider-independence-remediation.md) and [acceptance requirements](provider-independence-acceptance.md) retain authority over scope and completion.

The published comparison source is 168a856ae44e7431393b0a8a9404483dda294ccc, through migration 062. The coherent future implementation base selected during Phase 1 is 8f026c21ce2e633ba94368f63f3c01cac605f3d3, including unchanged 063–065 and their compatible readers, followed by reviewed forward migration 066 or later. This is a lineage decision, not installation, execution, interner activation, or permission to alter the frozen checkout. A 062 database plus 066 alone is not the installation sequence.

## Bounded contract

The new delivery discriminator is contractVersion = league-one-canonical-delivery-v1. The canonical schema is league-one-official-standings-v1. Public calls lacking the discriminator retain the exact legacy branch. An unknown discriminator, a mixed legacy/canonical top-level shape, a caller-supplied verification flag, or a function name is rejected.

The canonical SourceScope reuses the existing family value standings: kind=enrolled-resource; connectionId and leagueSeasonId from the authorized mapping; entityId=null; scoringPeriodId=null; audienceId=public; coverageSpecId=official-season-standings-v1. This is 2026 season-to-date data. No weekly finality, annual traversal or inferred league winner is added.

CanonicalMapping contains connectionId, leagueSeasonId, revisionId, generation, scope={provider,leagueKey,externalLeagueId,season,nativeNamespace}, and sourceNamespace. The scope nativeNamespace is the provider's league-key namespace. The root sourceNamespace equals the immutable mapping revision's season context, such as nfl:2026. They are different concepts and must not be substituted for one another.

The selected policy is returned by the private, deployment-owned canonical_resource_policy(mapping, delivery) function. Its complete allowlisted tuple fixes delivery/canonical/adapter/verifier/hash versions, public audience, standings coverage policy, provider/native kind and authorized team namespace. The application manifest must agree. A version string by itself grants nothing. The policy is copied into the existing scope identity and immutable attempt; the writer requires exact equality with the reserved policy.

The public JSONB input has exactly the following top-level keys. All are required except legacyInput, which is present only in a bridge submission. There is no second capture envelope or competing mapping nesting. Unknown keys, duplicate mode markers and explicit null in place of a required object reject. SQL-generated IDs, hashes and verification results are output, not caller authority.

Canonical decimals contain no exponent, leading plus, leading integer zeroes, trailing fractional zeroes or negative zero. Zero is the string 0. Numeric conversion uses PostgreSQL numeric and exact decimal handling, never floating-point addition. A 1,024-character canonical decimal ceiling is a defensive encoding bound covering every value produced by the existing finite-number Sleeper whole-plus-hundredths policy; a larger value is explicit invalid/capacity, never rounded. The complete canonical projection remains bounded at 1 MiB and 20 teams. Native payload transport limits remain the existing source limits, not an excuse to truncate evidence.

The canonical record omits Sleeper-specific sourcePath, whole, fraction and policy components. They remain in the retained native payload, the independently computed native projection, and the legacy facade. The Sleeper verifier must reproduce the current whole/fraction rules, including absent optional fraction, explicit null/invalid fraction, negative values and exact decimals, before projecting the common state/value pair. A standalone source does not invent whole/fraction facts.

No caller supplies a trusted seasonTeamId. Resolve or create the existing canonical team UUID from its verified sourceTeam reference and the authorized league/season connection. Preserve all old UUIDs. The identity design adds namespace-qualified uniqueness to existing identities; it does not create surrogate strings masquerading as native IDs or a second team identity system.

## Coverage and temporal semantics

Canonical ObservedCoverage uses entitySet=full/subset/unknown; the legacy standings DTO's partial value is a compatibility mapping from subset. periodIds is empty, interval=null, nextCursor=null for this complete-document slice. fields is the sorted subset of wins/losses/ties/pointsFor/pointsAgainst/providerRank/providerSeed known for every returned team; an empty team array has fields=[]. pagination is complete only from independently verified complete-document/page evidence, otherwise unknown; continuation is not admitted by this bounded slice. completeness is complete only for qualified full entity coverage and complete W/L/T/PF/PA, partial for qualified incomplete evidence, otherwise unknown. reasons is the sorted unique set of registered reason codes, at most 32 nonempty codes of at most 128 characters. The receipt additionally records expected_team_count, population=proven/unproved/mismatch and record_completeness=complete/partial/unknown.

Population proof must be independently interpreted by the registered verifier and bound to this acquisition:

- Sleeper uses the original linked league-document population evidence and its original source/witness relationship. Preserve 048:690–711 and effective 065 accessor semantics, including same acquisition or the qualified post-reservation timing rule. Do not borrow a previous head's count or require projection/scoring compatibility merely to display official standings.
- The synthetic standalone source supplies its own total/count and pagination evidence in its retained response. It needs no fake roster/configuration receipt. An explicitly supplied integral total in 1–2147483647 can prove population when it matches the distinct team count and its own completeness evidence; no total leaves population unproved.
- A supplied count mismatch retains reliable team facts but marks subset/mismatch. An empty array does not manufacture a proven positive population. Record completeness is complete only for a nonempty qualified result with every W/L/T/PF/PA known; rank and seed remain independently optional.

A structurally qualified partial/unknown standings snapshot can be retained and read as such. It never deletes omitted teams, merges a partial snapshot over a complete snapshot, or changes earlier immutable facts. Prior complete receipts remain explicitly selectable. Current selection still follows the latest reservation: a newer attempt without a receipt, invalid/capacity result, conflict or stale result is unavailable with its precise reason; it never silently falls back.

Retain requestStartedAt, requestCompletedAt, sourceObservedAt, checkedAt and normalizedAt as distinct values. Validate parsed timestamp types and request start ≤ completion ≤ checked ≤ normalized, source observation/source update ≤ checked when known, and checked/normalized no later than DB clock plus five minutes. Network bridge request times must be nonnull; pure fixture request times may be null because no HTTP occurred. Reservation/acquisition causality is additionally checked; clock comparisons do not replace a witness. Original sourceUpdatedAt/nativeRevision remain null when not actually supplied. Historical applicability stays unverified and freshness unknown unless the existing qualified policy supplies stronger evidence.

Each real capture receives its own immutable receipt, even when its content is unchanged. Exact replay reuses the same attempt, content, evidence and receipt; it does not generate a new observation time. Compare sourceUpdatedAt only when both current and incoming captures provide that same registered time meaning; sourceObservedAt, checkedAt, capture order and lexical nativeRevision do not become invented revision clocks. An older comparable sourceUpdatedAt cannot advance a head. Equal comparable sourceUpdatedAt with different canonical facts is a conflict; equal facts with a genuinely new acquisition can be recorded independently. Without comparable source update times the existing latest-reservation/generation rule governs, with freshness still unknown.

Reuse public.league_roster_resource_scopes, league_roster_resource_heads, league_roster_resource_attempts and league_roster_resource_acceptances. Fixture reservation context is exactly {version:canonical-fixture-reservation-v1,jobType:canonical-fixture-standings-v1,fixturePolicyVersion,policy,sourceLeague,intendedLeagueKey,season,registrationDigest,standingsDigest}. policy is the complete approved delivery policy object; sourceLeague is the full league ProviderReference; intendedLeagueKey and season are the exact admitted canonical key/integer season; fixturePolicyVersion is the pinned test admission version; each digest is the exact versioned SHA-256 text fixed by the source-pinned job/profile. begin_canonical_resource_attempt constructs this object from the actually locked job.payload and registered policy, never from a trusted caller object. Canonical content uniqueness includes connection/source identity, family, native kind, all content interpretation/hash versions, native_hash and canonical_hash. Hash equality is always followed by exact native_payload/canonical_value/version comparison before reuse; a same-hash/different-value collision aborts. The key does not include observation timestamps, attempt IDs or receipt IDs. Cross-provider/namespace content cannot be conflated merely because hashes match.

Add UNIQUE(id,connection_id,league_season_id) on existing scopes and new contents, UNIQUE(id,scope_id) on existing attempts, and UNIQUE(id,scope_id,connection_id,league_season_id) on new receipts. Canonical acceptances add FK(canonical_receipt_id,scope_id)→new receipts(id,scope_id), with that receipt pair also UNIQUE. first_receipt_id closure additionally checks content_id matches at deferred completion; the FK alone cannot prove the cycle.

Add the identity-design team UNIQUE(id,league_season_id,provider,source_league_namespace,external_league_id,native_namespace,external_roster_id), referenced by child(season_team_id,league_season_id,provider,source_league_namespace,external_league_id,native_namespace,external_team_id). On all new history relations, UPDATE and DELETE are rejected with the existing immutable-history mechanism. No runtime INSERT/UPDATE/DELETE/TRUNCATE grants are added. Content and typed children can be created only together with their first receipt in the same transaction. Deferred completion validates first-receipt closure, exact reconstructed canonical value, contiguous child count and the original attempt fence. A later transaction may create a new receipt pointing to complete retained content, but may not add or change its children.

The effective validate_current_roster_lineage() gets one explicit canonical-acceptance branch for the XOR target. Canonical acceptance requires a qualified receipt, the same scope/attempt/mapping revision, the current permitted policy, expected generation+1, the latest attempt, and original valid fence. It cannot be reached by giving a native wrapper a null legacy receipt.

The new trigger bindings are explicit: BEFORE INSERT on each new relation calls guard_canonical_resource_insert(); BEFORE UPDATE OR DELETE calls existing prevent_league_administration_history_change(); deferred AFTER INSERT on canonical contents and typed children calls validate_canonical_standings_complete(); deferred AFTER INSERT on canonical receipts calls validate_canonical_resource_receipt(); deferred AFTER INSERT on existing acceptances calls that same receipt validator only for a nonnull canonical_receipt_id. ## Hash and immutable evidence rules

New records use hashVersion=league-one-jsonb-sha256-v1 and lowercase sha256-prefixed hexadecimal output computed by SQL. The recipe is SHA-256 over UTF-8 of a specifically constructed JSONB object's PostgreSQL text representation. The native domain includes hashVersion, representation=native, nativeKind, adapter version and the parsed native payload. The canonical domain includes hashVersion, representation=canonical, canonicalSchemaVersion and canonical_value. Array order is significant; JSONB object key/number rendering follows this versioned SQL recipe. Record the PostgreSQL version in qualification evidence; do not replace the recipe without a new hash version.

The receipt evidence hash uses a separate versioned JSONB domain containing: full immutable attempt identity, nonce and canonical_reservation_context (including explicit null for bridge); exact mapping, scope and policy; content ID plus native/canonical hashes and all versions; original provenance; verified native source reference/legacy receipt link; verified population/coverage; and qualification/outcome. It excludes the new recorded_at clock so an exact replay does not retimestamp or rehash its evidence.

No caller-provided hash establishes parity or source authority. The database recomputes the new hashes. Existing compatibleRevision/stableJson native hashes and JSONB receipt hashes keep their original definitions and values. A parsed JSONB payload is not proof of original HTTP bytes or lexical JSON formatting. Do not rehash legacy records into the new domain or label them newly acquired.

The verifier result has exactly {canonicalValue,coverage,expectedTeamCount,population,recordCompleteness,qualification,reasons,nativeSourceRef,legacyRosterReceiptId}. It is constructed internally; the public input cannot provide it. The fixed registered dispatch constructs private adapter context from the already shape-validated submission, immutable attempt/policy and, for a bridge, the native receipt selected by the reserved native attempt. Pure verifier functions accept that context, not an arbitrary asserted verified flag. Deferred validation reconstructs the same context from stored content, receipt and original native evidence; it need not retain or replay the legacy write command. This separates parity verification from write orchestration while keeping both independent of the application normalizer.

Canonical structural/coverage reason codes are exactly standings_identity_invalid, standings_team_limit_exceeded, standings_byte_limit_exceeded, standings_decimal_limit_exceeded, standings_population_unproved, standings_population_mismatch, standings_capture_partial, standings_record_fields_incomplete. A future reason/semantic addition changes the registered validation policy; arbitrary caller strings do not silently extend it.

## Real acquisition and the Sleeper compatibility bridge

For a selected Sleeper core capture, reserve the canonical standings attempt before the original players attempt. Both use the same authorized source mapping, provider identity, original job fence and admitted dispatch. Then the existing application adapter performs its existing HTTP acquisition once.

The public canonical dispatcher receives the canonical delivery plus the original native legacyInput. Its fixed Sleeper orchestration branch validates the basic bridge binding, invokes the private legacy dispatcher exactly once with that original JSONB input, then passes the actual newly written roster receipt through internal verifier context. The pure private Sleeper verifier checks native/canonical parity and evidence binding; it does not itself invoke a writer. Any mismatch aborts and rolls back the entire transaction. The legacy input is not augmented with canonical fields or a new witness version, so its content/receipt hash definitions remain unchanged. The canonical receipt binds to that exact legacy receipt, payload, original witness and pre-reserved canonical attempt. The native path remains compatibility/evidence for the existing core resources; it is not another acquisition, queue or independent standings publication. A preserved native receipt due only to incomplete player membership may still supply independently valid standings evidence; canonical acceptance does not require the native players head to advance.

The current witness derivation enumerates every reservation under a fence. A narrow forward change to derive_public_data_capture_witness(JSONB,JSONB,JSONB) is required; claiming it can remain entirely unchanged would be incorrect:

1. Partition reservations exhaustively into the existing native roles and at most one explicitly recognized canonical standings companion, only for core work under the declared Sleeper policy.
2. Validate the companion's full policy/scope, UUID/nonce, source namespaces, connection/revision/generation and same fence. Its reserved_at must be within the same dispatch window and no later than the native players reservation.
3. CanonicalMapping adds namespace fields; compare its validated lossless legacy projection with the original native mapping. Do not drop unchecked fields or require raw JSON equality between different mapping versions.
4. Preserve all exact native role sets, duplicate/unknown-role rejection, dispatch nonce/work/intake checks, 30-second admission limit and final owner recheck. The returned native public-network-capture-v1 value contains the original native roles only. The recognized companion is bound separately in the canonical receipt.
5. Reject a second companion, another resource/policy, a companion for non-core work, namespace/remap mismatch or missing native players role. There is no general “ignore unknown reservations” escape.

A new bridge receipt requires a newly created native roster receipt in this transaction, matching the existing source restriction. It also requires canonical.reserved_at ≤ nativeAttempt.reserved_at; identical original fence and source identity; payload/native content equality; original witness and native receipt validation; and current live ownership after all locks and at deferred closure.

Exact replay is different: if the same canonical attempt already has a receipt, all input/evidence must match the previously bound canonical/native pair. Return it without inserting a new receipt, changing times or attaching a different native receipt. An old standalone legacy receipt cannot be attached as a fresh canonical observation. Retained history uses the legacy read codec unless a separately scoped replay design is approved.

No new standings public work kind, recurring task, request-budget lane or provider fetch is added. Existing checkpoint/request-budget functions are not generalized merely to count canonical sidecar rows as additional captures.

## Standalone fixture route and proof data

The isolated fixture adapter uses the same public writer, common state tables, private common acceptor, canonical materializer and reader. It has no legacyInput or roster receipt. Its native JSON uses a different structure: leagueKey, seasonTag, teamTotal, page={complete,next}, and entries with clubKey, played={won,lost,tied}, totals={for,against}, place and seedNumber. Native points are decimal strings. The independent fixture SQL verifier maps these keys to the exact canonical contract; it does not call the application normalizer.

The fixture namespace and source keys include punctuation and case, such as club:ABC-7, with deliberately colliding bare IDs across two registered sources. Duplicate source references, unexpected namespace, invalid totals and malformed decimals have explicit negative cases. The team total/page flags are interpreted from the retained native response; an application completeness flag alone does not prove coverage.

Qualification uses two distinct, explicitly labelled modes:

1. Pure offline translation: both synthetic standalone evidence and a retained Sleeper translation sample have origin=fixture, no legacyInput and no fake native receipt/witness. The isolated source-pinned private policy enables these exact cases; production rejects them. The Sleeper sample uses its independent native projector while entering the same canonical acceptor/materializer as the synthetic sample.
2. Protocol bridge simulation: the existing adapter/protocol runs against mocked fixture transport under the guarded harness, with real isolated DB reservations, nonces, dispatches, fences and legacy receipt creation. legacyInput and canonical bridge provenance retain the protocol-required origin=network and original public-network-capture-v1 shape; the unchanged native guard therefore remains exercised. This value describes the exercised protocol, not actual provider acquisition. The pinned run manifest marks providerSimulation=true, identifies every mocked transport response and enables a provider-network tripwire that fails on an actual provider request. No report may call this a real provider capture. The simulation manifest is qualification evidence, not an accepted runtime trust flag, new production input key or relaxation of native guards.

Pure fixtures register through the same runtime registerCanonicalLeagueSeason method / register_canonical_official_source RPC under the fixture-only admission branch. Existing public intake cannot admit these sources: its numeric-ID candidate and Sleeper user/list FKs are not fabricated or bypassed. Restricted runtime calls the real acquireJob path for the policy-bound projection_jobs job of type canonical-fixture-standings-v1; that existing method may create/claim the row, so owner-seeded jobs are not a prerequisite. The immutable execution manifest and stored job.payload fix policy/version, intended canonical leagueKey, exact source league/season, registration native digest and standings native digest. The private fixture policy checks those values and the actual live lease owner, generation and deadline before/after lock waits and before commit. A caller cannot choose an existing canonical leagueKey to bind an unrelated source. No owner-seeded source identities or extra worker/table is introduced.

Fixture acquisition evidence is exactly {version:canonical-fixture-capture-v1,jobKey,generation,attemptId,nonce,sourceDigest}; every value is checked against the real job, attempt, input digest and pinned test policy. The DB-issued nonce and stored job payload bind the registered mapping/source, not a caller-declared fixture flag. The simulation's Sleeper registration retains its actual guarded public-intake path and fixture-native source shape. Both modes exercise restricted writes and stored reads; only the simulation exercises native protocol/witness closure. Neither qualifies real provider HTTP. Live production proof remains separately scoped and unauthorized here.

## Transaction and reader algorithm

The new reservation and writer retain the lock order: current job/owner → existing league-configuration advisory lock and source connection → resource head. Validate live fence before work, after lock waits, before head advancement and at deferred receipt closure. Store the original fence in the immutable attempt. Source remapping or loss of ownership cannot be repaired by replacing that fence.

Within the writer transaction: select the registered policy; validate exact input shape; lock/check the current job, mapping and existing attempt identity/nonce; validate basic bridge binding when applicable; invoke the private legacy writer once to create the actual native receipt (or identify the already-bound pair on exact replay); then run the pure registered verifier against that internally resolved receipt and the retained native/population evidence. A standalone fixture goes straight to the pure verifier without a legacy call. Lock the canonical head after the job/mapping locks; compute hashes; compare exact replay; insert or reuse immutable content; resolve qualified team identities; materialize complete typed children; insert the new receipt; then append the XOR canonical acceptance and advance the same head only when latest ordinal, expected generation, source-time and qualification rules permit it. Rejected/stale/conflicting evidence stays explicitly classified and does not advance an accepted head. An SQL exception rolls back the entire statement, including any compatibility bridge writes.

The internal store API is readCanonicalOfficialStandings(mapping, selection), with selection exactly {kind:current,representation:canonical-v1|legacy-sleeper-v1} or {kind:receipt,representation:canonical-v1|legacy-sleeper-v1,receiptId:UUID}. representation is required; no automatic retry in the other representation. The existing readOfficialStandings API remains unchanged. These are internal store operations, not new public routes or UI cutovers.

The new reader result is a discriminated union. Canonical available: {status:available,representation:canonical-v1,scope,mapping,selection,facts,teams,receipt,coverage,expectedTeamCount,population,recordCompleteness,freshness:unknown,historicalApplicability:unverified,versions}. facts is the exact canonicalValue; teams adds only resolved seasonTeamId beside each canonical team fact; receipt={id,contentId,attemptId,ordinal,acceptedGeneration,provenance,nativeSourceRef,legacyRosterReceiptId,outcome,reasons}, where acceptedGeneration is integer or null and legacyRosterReceiptId is UUID or null. versions={contractVersion,canonicalSchemaVersion,adapterVersion,nativeVerifierVersion,canonicalNormalizerVersion,hashVersion}. For legacy representation the recorded legacy codec supplies the compatibility facts and evidence through a tagged legacy result, not fabricated canonical versions: {status:available,representation:legacy-sleeper-v1,legacy:the available variant of OfficialStandingsRead}. All other results are {status:missing|unavailable|disabled,representation,reason,attemptId:UUID|null,receiptId:UUID|null}; conflict is unavailable with reason=source-time-conflict, not available with an estimated winner.

Current selection first selects the latest reservation for the explicitly selected scope/representation, then its receipt, qualification and acceptance. Absence of any attempt returns missing; a latest attempt without a receipt returns unavailable with reason=pending; invalid/capacity returns unavailable with its retained reason; stale/conflicting/generation-preserved results are unavailable for current selection. An explicit historical receipt selection can return its independently qualified reliable facts with acceptedGeneration=null and the retained outcome in the receipt when it did not advance a head. In particular, a preserved-conflict receipt is available only as explicitly selected, labelled source evidence, never as an accepted official current result. It verifies the historical mapping revision and source scope without relabelling it as current. A later legitimate remap must not make immutable historical evidence unreadable. A current qualified partial result remains available with explicit coverage.

Reader selection is an explicit versioned policy: legacy scope/receipt uses the recorded Sleeper legacy codec and 064/065 accessors; canonical scope/receipt uses the common decoder and canonical tables. Unknown versions or conflicting evidence are unavailable, not a reason to retry a different head. The existing public legacy facade keeps rosterReceiptId and native whole/fraction details only when backed by an actual legacy bridge/record. Standalone canonical results never fabricate those fields and are not exposed through an incompatible public facade.

New canonical mode remains disabled for production selection until its slice and release gates are satisfied. Disabling it stops new selected canonical admission under the existing owner, retains both readers and all accepted history, and does not revert to a build incapable of decoding already stored canonical records.
