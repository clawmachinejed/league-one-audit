# Exact native-period matchup shadow resource

This Bundle 1 change adds an internal accepted matchup-period read through the existing administration acquisition, normalizer, writer and Neon store. It does not switch a page or API, add a provider/Tank01 request, change a cron cadence, score a player, republish a snapshot or enroll a provider. The [Step 2 ledger](step-2-checklist.md) remains the completion authority for the entire bundle.

## Identity and evidence

- Scope is the enrolled connection, league-season UUID, public audience and Sleeper native matchup week 1–18. `sleeper:matchup-week:<week>` is a provider competition period, not an asserted NFL week. A league settings document does not establish NFL-week mapping. The returned `nflWeekMappings` list is empty until separately qualified calendar evidence is joined.
- Exact capture receipts reuse the PR267–269 attempt/head/acceptance tables. A reservation precedes the existing uncached matchup GET. It carries the current mapping revision, period, latest ordinal, accepted generation and optional worker lease. The single existing administration writer stores its v1 observation once and attaches a shadow receipt/acceptance in the same transaction. No shadow resource advances from an ordinary cache check. The existing changed-cache verification path reserves before its already-required network fetch; without a same-run configuration proof it retains evidence but preserves the last accepted head.
- A complete all-team **participant inventory** needs the independently captured network league document's `total_rosters`, exact stored configuration content, current v1 configuration head, unique matchup roster IDs, corresponding existing season-team IDs and a complete source payload. The SQL receipt claims coverage only for `roster_id` and `matchup_id`; lineup and score fields report their own gaps in the typed read. A partial capture, even with a full row count, may be retained but cannot replace the complete head. Missing team score or lineup fields do not become zero or empty arrays.
- Matchup identity includes the season and native period. A non-null native matchup ID groups participants; a null ID creates one unpaired team, with no synthetic opponent. Three or more participants remain visible but result support is limited. A corrected grouping is a new immutable content/receipt version, not a mutation of prior history.
- The read projects raw player score and lineup fields from the *same stored content* as the v1 normalized matchup, then re-normalizes and checks the legacy value/hash and linked season-team identities. Starter-index score takes precedence over `players_points`, including zero. Official team effective points use `custom_points ?? points`, including explicit custom zero, and are never rebuilt from player scores. Source numeric JSON values remain JavaScript numbers; no missing lexical decimal precision is claimed. The raw and custom values are both retained. A custom override identifies adjustment evidence, while its reason remains unknown unless supplied by the source.
- The period's players minus starters form bench evidence only when the same captured league document says `status: in_season`, identifies that native week as its current `leg`, and supplies a matching starter-slot count. Otherwise the bench is unknown, even if the raw source lists nonstarters. Missing players or starters is unknown; a proven `[]` is empty. Historical IR/taxi are unknown; current roster group metadata is never overlaid on a past bench. Raw starter indexes and vacancy markers remain available without a proven slot label. Current catalog metadata is never asserted as a historical fact. Provider finality is unknown from the matchup payload; the local site calendar, NFL game state and existing forecast/probability outputs remain separately scoped references.

## Retained native-to-NFL mapping continuation

The dependent Mapping increment adds migration `031_native_period_mapping_evidence.sql` and connects its evidence to the internal accepted-matchup reader. Each sidecar binds the pre-acquisition connection/mapping revision, league-season UUID, exact accepted league configuration content and originating observation. Its versioned adapter policy interprets Sleeper native matchup endpoint weeks 1–18 as the corresponding NFL regular-season weeks. The configuration must explicitly identify the same Sleeper league, season, NFL sport and regular-season format. Fantasy playoff stages remain separate from NFL season type. The shared full-season validator and existing `resolveSiteWeek` validate the complete 272-game inventory and real dates within that season; unsupported older 16-game schedules do not acquire invented coverage. This proves a weekly leg, not all legs of a multiweek fantasy contest.

The retained document carries the actual requested schedule season/resource, minimal canonical schedule rows, schedule and policy revisions, evaluation time and retrieval interval. The existing one-hour framework cache does not expose the provider acquisition time, so `sourceObservedAt` remains null. Retrieval or evaluation time is never relabeled as network freshness. Semantic deduplication excludes those changing invocation timestamps: equal evidence retains its original ID and dates, while a changed schedule revision has separate immutable lineage. The reader selects the first retained compatible proof deterministically and validates it again; it does not claim to select the latest calendar. An A-to-B-to-A schedule replay therefore preserves the original A proof. A source-connection A-to-B-to-A remap has a new mapping revision and cannot borrow the original proof.

The period's `nflWeekMappings` is populated only when that separate proof qualifies. Missing, invalid or conflicting optional evidence leaves official participants, scores, lineup facts, receipt coverage and original source times unchanged. No current authority, fantasy finality, historical slot applicability or forecast readiness follows from the mapping. A later sidecar may support an earlier receipt only when its immutable configuration content and source revision match exactly; the original receipt is neither rewritten nor restamped.
