# Selected relational and transaction design

This document specifies the reviewed first-slice logical and candidate physical design decisions for the [foundation](README.md). Source baseline for this design review is documentation HEAD `e2a37d9`; application source remains the separately verified baseline. **Selected design, not implemented or database-qualified.** The companion [relational-design.json](relational-design.json) contains 135 field mappings, 17 storage responsibility groups, 44 computable logical relation schemas, explicit dependencies and decomposition arguments. These counts are inventory, not a test score. The missing engineering choices are now selected as ENG01/ENG02 in [the decision register](backend-decisions.md), with [structural SQL](proposed-schema.sql), [ER diagrams](relational-erd.md) and [exact admission contracts](acquisition-admission-design.md). Implementation/catalog/provider/capacity and release qualification remain G6/G7 work.

The field semantics in [contracts](contracts.md) and [foundation.json](foundation.json) remain authoritative. This document chooses their storage and synchronization realization through existing owners. Proposed names below are concrete reviewable migration candidates, not tables/functions claimed to exist. No migration, runtime, credential, data, cron, public-route or worker deployment is performed. D02 stays exactly 3,600 seconds; D03, D04 and D05 are selected in [the decision register](backend-decisions.md); their migration, conflict/recovery, retention and release evidence remain activation gates.

## Selected model and storage

Keep L1 actor, provider identity, association, acquisition authority, manager role, preference and shared league evidence separate. One shared team resource serves different eligible actors; no ownership transfer occurs when someone follows, disconnects or expires. A stable league has independent season rows; each association chooses one current season for that league. Annual provider aliases never replace internal league/route identity.

The JSON's `storage_responsibilities` specifies exact existing columns, proposed additions, keys, relationships, constraints and writer ownership under RD01–RD17. `field_mapping` covers every registered first-slice field individually, including derived values and absent/unknown semantics. Transient results do not become seventeen physical tables. `relations` models logical relations LR01–LR41 (including typed identity-evidence subrelations, stable team-source relation and selected admission scaffolding) for independent attribute-closure analysis.

Select these additions where current source has a demonstrated gap:

- Immutable pre-enrollment request/capture/identity evidence extends the existing provider request and administration owner. Failed transport needs no invented league, mapping, normalized timestamp or accepted content.
- A revisioned public acquisition context supplies explicit audience/permission identity. It stores no credential and grants no serving entitlement.
- Per-season discovery checkpoint/candidate relations retain continuation and complete-list receipts. A partial unique index identifies at most one unfinished run; actual `finished_at` distinguishes completed/explicitly terminal history. A later explicit refresh uses a new scan UUID and new receipts even when the association/strategy/query set is unchanged. Retryable failed work retains its unfinished ID and continuation. Arrays in the API are projections of these relations.
- Existing links gain derived provider and qualified subject-lookup references. Two active partial unique indexes enforce exclusivity; trusted composite equality prevents a submitted provider mismatch.
- User current selections and immutable renewal proofs preserve same-league and both-mapping relationships.
- An unfollow tombstone accompanies the existing preference DELETE; a later explicit follow receives a larger revision. Existing public saved-row behavior remains until authorized cutover.
- One authorization generation on each existing source connection, with immutable authority events and captured reservation generation, fences all relevant accepted manager versions. This is a fence over the existing writer, not another normalized head or ingestion pipeline.
- Qualified-policy metadata and a serving-binding relation choose one existing versioned resource head. The head's acceptance is joined at read time rather than copied into another mutable pointer.
- Existing durable `projection_jobs` or applicable existing pending-state rows carry required downstream intent in the acceptance transaction; no new outbox or scheduler is selected.

RD08 selects official-only admission by allowing a NULL original scoring attachment **only** on explicitly marked new official-only season rows. Existing non-null attachments and the immutability trigger remain unchanged. Later qualified analytics attaches through versioned configuration applicability, never by changing an old season's scoring attachment. Before target admission is enabled, legacy analytics enumeration must explicitly exclude unsupported official-only rows and return unavailable coverage; no dummy scoring rules or silent join-drop may masquerade as supported analytics. This is a candidate future migration/runtime dependency, not approval to apply it.

All logical relationships have specified optionality in RD01–RD17. Composite foreign keys enforce same-league seasons, same-season teams, connection/mapping correspondence and accepted head scope wherever representable. Cross-resource receipt/audience/coverage equality uses guarded writer validators in addition to FKs. A CHECK expression reading another mutable table is not selected as a substitute for referential integrity.

## Normalization and decomposition

Use functional dependencies from business meaning and source constraints, not accidental values in one sample. Candidate keys in the JSON are minimal determinants under the listed domain dependencies. Conditional active uniqueness does not become a global historical key: two ended links can share an actor/account pair. NULL alternatives are tagged and validated; a nullable source reference is not treated as a universal candidate key. A lookup capture resolves exactly one manager, so LR06L's key is `lookupCaptureId`, not a redundant pair. LR04 and LR34 are enforced current singletons: each logical candidate key is the empty set ∅, with ∅ → every attribute. Their physical SQL `PRIMARY KEY(slot)` plus `CHECK(slot=1)` (LR04) or `CHECK(slot='membership')` (LR34) enforces at most one row; `slot` is not claimed to be a minimal logical key. LR05 and LR21S deliberately describe provider-neutral logical domains. Their implemented physical Sleeper-only restrictions have additional constant dependencies and smaller keys; preserving the physical composite indexes does not make them minimal logical keys or implement another provider.

The logical core separates independent actor/login/provider/association facts. LR07 explicitly remains a constrained projection because existing assurance is the constant user_asserted: empty set determines assurance without determining the association. No needless constant table or existing-schema rewrite is selected. LR22's semantic key excludes role because qualified owner/co-manager sets are disjoint; its existing role-including SQL primary key remains a physical superkey. A source row's immutable capture ID determines its observation time; a reused content hash does not. Mutable multivalued discovery requirements, manager roles and user preferences have separate logical relations. Source payloads, snapshots and transition certificates remain immutable typed documents with deliberate repetition. Their `document` classification makes no assertion that arbitrary internal JSON is relationally normalized.

The projection/document schemas explicitly list known dependent duplication: selected season determines stable league; mapping revision determines connection/season; list capture determines its season; configuration version determines its league season; observation determines content. SQL indexes and constrained pointers may retain those values for scope enforcement. No blanket claim that every physical table is in BCNF or 3NF is made.

Five decompositions have machine-readable FD sets and a lossless/dependency-preserving argument:

1. **DC01 association/provider:** factor the physical association/provider dependency into an intermediate association projection and provider identity. The intersection `providerAccount` determines the provider relation. Joining cannot invent another provider; `association → provider` follows through providerAccount. DC04 then removes the intermediate projection's repeated manager. The physical copied provider supports active actor/provider uniqueness and is checked by a NOT NULL composite FK. The physical extended link is intentionally not claimed 3NF.
2. **DC02 season/route:** decompose season identity from stable league/route identity. The shared league key determines the route relation; season-to-route follows transitively. Route keys are joined, not copied into season storage.
3. **DC03 capture/content:** separate immutable bytes from each retrieval/verification receipt. The shared content ID determines bytes. This retains duplicate retrieval evidence and prevents content deduplication from refreshing a clock.
4. **DC04 association/lookup subject:** a qualified lookup capture resolves exactly one provider manager. LR07 retains the lookup reference; LR06L supplies its manager. Shared `lookupCaptureId` determines the right relation, and both original dependencies remain local. The physical link may retain manager for active exclusivity only with the exact composite lookup/manager FK; unqualified legacy NULL lookup never grants target access.
5. **DC05 historical team/stable source:** split team identity `(team,connection,externalLeague,nativeTeam)` from stable `(connection,season,provider)`. The shared connection key determines the right relation and all listed dependencies stay local. Current `(provider,externalLeagueId)` uniqueness is **not** a historical FD: migration 026 remaps the current connection while migration 016 retains old season-team rows. An old alias may subsequently be current on another connection. The old season/team cannot merge with the new one. A team joins its stable connection through `(season,provider)`; its historical alias is checked against its captured mapping rather than FK'd to today's alias.

Other normalized logical relations have all declared nontrivial determinants as superkeys. Documents/projections carry explicit exceptions, consistency owner and validation mechanism instead of unsupported normal-form certification. Root review computes closure/key minimality and checks these stated claims independently; that proves the finite declared dependency model, not completeness of undiscovered business semantics or deployed SQL enforcement.

## Selected transaction protocols

**TX01 — Same-transaction auth and ordered domain locks (ENG01).** Retain account **ReadCommitted** and existing timeout ceilings. Every protected read or mutation first calls the narrow migration-owner `public.lock_account_session_authority_v2(jsonb)` inside account transaction **B**. This helper acquires shared `pg_advisory_xact_lock_shared(19740517,1)`, then the active epoch, exact auth user and exact session FOR SHARE. B owns these database locks through its own commit/rollback, including coordinator death while B continues. A separate client-held auth transaction is no longer the authority-lifetime proof. No provider HTTP request occurs inside B.

The trusted maintained Better Auth wrapper validates the actual cookie with cache/refresh disabled and applies the existing verified-email/invitation rule unchanged. It creates exactly nine server-only `AuthReceiptV2` fields: `{sessionId,subject,expiresAt,issuer,admissionEpochRevision,configHash,clockDomain,admittedEmailDigest,sessionTokenDigest}`. IDs retain opaque source types; revision is a positive decimal BIGINT string; expiry is a canonical UTC timestamp. Digests are lowercase 64-hex SHA256 of **exact UTF8 persisted** admitted email and validated session token, with no trimming/case folding before hashing. They are sensitive ephemeral parameters, never HTTP input, cached proof, job data, logs or audit metadata. Existing invitation canonicalization remains solely with the maintained bridge; matching exact current email digest plus unchanged config binds the same decision without inventing a second SQL allowlist.

The helper validates closed shape, actual epoch/config/issuer/database clock, current emailVerified, email/token digests, exact session ID/user/expiry and unexpired authority. It returns only `TABLE(session_expires_at timestamptz,admission_epoch_revision bigint,db_sample_at timestamptz,session_created_at timestamptz)`. The fourth value is the actual locked session creation time; D03 own-release requires DB age at command admission from0 through300seconds inclusive, never a submitted timestamp. It is **auth-only**: after it succeeds, every composition path locks active Actor then exact login identity and validates issuer/subject/actor binding. No account/runtime raw auth schema/table grants are added. Actual pgcrypto extension/function identity is catalog-qualified. Changed token prevents session-ID ABA; changed email/admission or missing session fails closed.

The trusted bridge sets transaction-local `app.session_receipt_v2` before existing private SQL. Legacy account BEFORE STATEMENT guards invoke auth first and then actor/login binding; target helpers invoke it unconditionally from their typed receipt. The existing login resolver keeps its signature but consumes the same receipt, binds issuer/subject, authenticates **before** its special registration mutex, and then locks Actor before login for existing identities. Brand-new actor/login allocation is owner-only authenticated bootstrap and binds the resulting identity before return. An actor-held caller may not enter this resolver; a generic context flag cannot bypass authorization.

After auth and (only for resolver) registration mutex, acquire actor/login, provider-manager and association; typed immutable request/command ID mutex; acquisition context/policy; stable league and sorted source connections; current selection, preference and serving binding; then admission provider gate and demand/job/permit locks where applicable. Within each class sort exact keys. Read locks are FOR SHARE; writes FOR UPDATE. Connection creation first locks stable league, fencing absent-connection enumeration. Source policy/binding mutators participate in the same earlier context/policy/stable-league order; no connection-held path acquires an earlier lock. Worker claim is a separate provider-gate/demand/job-only transaction and ends before domain reservation.

Trusted operator revocation uses only `public.disable_app_actor_v1(uuid,uuid)` and `public.revoke_app_login_identity_v1(uuid,uuid)` under the catalog-pinned migration-owner **session_user** identity, never a caller-set flag. They take exclusive auth gate → Actor → sorted login locks, perform only their named action and require existing operator audit. Application roles cannot execute or assume the owner. The statement guard has this explicit role-authenticated owner branch, so disabling a compromised actor does not require that actor's live cookie. Resolver login INSERT instead has shared auth-only statement participation plus exact NEW actor/issuer/subject binding; UPDATE/DELETE login mutations use the owner-only branch. The SQL manifest specifies this boundary, including the inherent trust in schema-owner maintenance.

Every relevant auth mutation obtains the **exclusive** existing auth gate before tuple locks, through BEFORE STATEMENT triggers/owner entrypoints, including direct supported user/session/admission-epoch DML. Every account/domain mutator, including old APIs and supported operator paths, joins its declared ordered guards. Existing audit/rate subject branches retain behavior; new subjects use explicit adapters. The auth helper alone does not establish actor ownership, membership or source coverage.

Once ordered locks are held, a fresh ReadCommitted statement reads the selected immutable refs and **entire applicable** cross-version adverse/positive set. Shared connection fencing blocks changed rows and newly qualified additions. Immediately before final account SQL, anchor monotonic time. The final decision samples database `clock_timestamp()` and evaluates actual session/admission deadlines, D02 exactly 3,600 seconds where membership is required, and applicable finite acquisition expiry using that single verified database clock. A command's linearization point is this last guarded decision in B; locks hold revocation until B finishes. Final statement must leave no later domain work that could bypass its decision.

Read success returns server-only `{result:ReadCurrentRosterResult,decisionTiming:DecisionTiming|null}`; command envelopes follow below. `DecisionTiming` is exactly `{dbSampleAt,minimumAuthorityExpiresAt,remainingLifetimeMs}`. Instants are canonical UTC strings with three fractional digits truncated toward earlier millisecond. Remaining lifetime is the decimal integer floor of original database numeric milliseconds, not subtraction of displayed strings. The minimum includes every applicable finite authority deadline; mandatory missing/invalid/nonfinite authority fails closed. Denied/indeterminate gets null timing.

After B confirms commit, validate its result and compute `remaining = parsedRemainingLifetimeMs - ceil(monotonicElapsedMilliseconds)` from the anchor before SQL dispatch. Require strictly positive lifetime and overall request budget immediately before synchronous serialization/body handoff, with **no await** between the final check and handoff. Strip all timing/auth sidecars. Unknown/backward timer, exhausted budget or unknown commit returns safe indeterminate; never infer rollback from transport abort. No application wall-clock subtraction, automatic final-read retry or recall of already delivered bytes is claimed.

The account/auth deployment must prove the same actual PostgreSQL/clock authority and exact role/catalog manifest. Existing account 3-second lock, 8-second statement and 12-second outer request ceilings remain maxima, not SLAs. A statement timeout is not a total transaction lifetime proof; database-owned locking and final response checks have distinct roles. A missing guard or unqualified catalog fails closed for this path while L1 sign-in remains independent. See [ENG01 exact failure schedules](acquisition-admission-design.md) and [SQL guard manifest](proposed-schema.sql).

**TX02 — Exclusive activation.** In the global order, lock actor, login identity, then the stable provider-account row before association rows. Resolve a successful immutable lookup for the same provider/namespace/native account. Check expected actor revision and existing live association. A repeat of the same already committed association returns its ID; a distinct active claim conflicts privately. Insert the link, derived provider, subject-lookup reference and existing audit in one transaction. Both partial unique constraints are the final arbiter even if another actor races. Existing conflicting rows stop the migration/activation; no winner is chosen. Ended links are immutable history, not candidates for reactivation. D03 requires authenticated own release or independently validated implemented provider-control proof before a conflicting claim can move; unsupported disputes remain locked. No automatic claimant displacement.

**TX03 — Capture/acceptance and durable work.** The existing reservation owner locks the relevant context/connection before resource head/job lease rows, validates current mapping and lease, and reserves its head-local ordinal/expected generation. New target reservations retain the current connection authorization generation and authority event reference. Commit reservation **before** the bounded provider request. Pre-enrollment attempts additionally serialize on their typed request ID: all attempts for one immutable request must retain the same scope/context/revision.

On response, the existing administration writer reacquires the same ordered fences. It validates exact capture lineage and independently qualified manager/held groups. In one transaction append observation/content/receipt, append acceptance, move the correct versioned head, append a membership authority event and increment the connection generation when applicable, and insert each actually required existing pending-work marker/job. Failure rolls back all of these. If no rebuild is required for a direct stored read, do not invent a job. Claims and publication retain their existing job/lease/deadline guards.

A successful acceptance is not interchangeable with failed transport evidence. A failure receipt stores actual known request/attempt timestamps, with normalizedAt NULL if normalization never ran. It cannot produce an acceptance generation or advance membership freshness. The successful/failure receipt alternatives are exclusive under the locked attempt; retries use another reserved attempt and preserve the original failure.

**TX04 — Cross-version removals and proved supersession.** A connection's authorization_generation is the **set fence**, separate from every head's ordinal/generation. Qualified manager acceptance, addition/suspension of a qualifying policy, source remap and serving promotion all acquire that connection FOR UPDATE and append/increment atomically. The final reader's FOR SHARE blocks both changed rows and newly added relevant rows: insertion must acquire the common parent lock first. A guard trigger and revoked direct table writes close the bypass. A passed list of old references alone is insufficient.

All immutable adverse membership events whose source evidence was qualified **when admitted** remain in the decision's adverse set, even if that policy is later suspended, its serving binding is reverted or its current head moves. Suspension prevents using a positive allow; it does not erase an admitted removal. Only the existing proved later fresh verification rule can clear that removal. Unresolved validity stays fail closed; never rebuild the adverse set solely from currently qualified heads.

For the linked provider manager, evaluate qualified positive evidence and every still-applicable complete-removal receipt for the selected season/current compatible authority. Unqualified shadow versions cannot create authorization. Unknown role population cannot prove removal. Scope incompatibility or uncertain ordering cannot create an allow.

A later correction can supersede a removal by either (a) a documented comparable provider revision proving later applicability, or (b) a **new qualified network attempt reserved after the removal was committed and observed under the connection fence**, with reservation_authority_generation at least the removal's event generation and current mapping/context/association still valid. Its immutable attempt is the orderingEvidenceRef. Equal generation is allowed only because reservation acquired the lock after the removal event committed; the event/attempt causal ordering is verified, not inferred from numeric equality alone. No previously reserved attempt, cache, replay, later arrival, local head ordinal or version label qualifies for fallback (b). If another removal commits during that request, revalidate against it; the attempt cannot supersede that newer event and fresh revalidation is required.

Fallback (b) proves a fresh League One verification after awareness of the removal, **not the provider's hidden event chronology or consistency**. D02's provider-current qualification remains an empirical adapter assumption, and unverifiable/contradictory evidence returns denied/indeterminate. A promoted old positive cannot erase a known removal. The same binding/connection lock protocol applies to rollback and its required pending work; frozen baselines never change.

**TX05 — Current selection, renewal and unfollow.** Lock actor and association; lock both stable league/source connections in deterministic order; lock the current-selection row and authoritative preference/tombstone. A missing selection/preference cannot race an insert because every such actor-scoped writer takes the already-held actor lock first. Validate both mapping revisions, same stable league, later successor season, nonforked lineage and fresh current successor role proof. Compare captured association/selection revisions and captured follow revision. Write immutable renewal proof and CAS the selected season atomically. An existing follow is carried only if its expected revision still matches; no follow means no carry. A newer unfollow/tombstone wins. An explicitly new later follow is a separate user command, not renewal inference. D04 preserves explicit follow intent while effective serving/collection is suspended; unchanged intent revision plus fresh qualification can resume it. Explicit unfollow is never resurrected.

**TX06 — Source remap and policy promotion.** Retain immutable mapping revisions and the current composite pointer FK. Lock connection, append the new mapping generation and update pointer via the existing guarded owner; increment authorization generation. The same native ID returning in A–B–A never restores the old revision ID. Pending requests/materialization must match current captured mapping, authorization/binding and lease fences. Policy qualification and serving selection have exact full-scope keys; no semver/time automatic selection. Commit binding revision and required durable work with the parent event/fence.

**TX07 — Admission/configuration deployment.** An auth deployment must present its exact nonsecret admission configuration hash and issuer to the active epoch helper. Old and new deployments can coexist but only the active hash is admitted. Operator activation takes the exclusive auth gate and increments epoch; active shared readers finish before the change, later requests on stale code fail closed. Credential/allowlist changes still require their ordinary authorization and safe rollout; no secret is copied into this document or app tables. The database-side guard covers direct user/session changes as well as wrapper routes. Auth token verification remains Better Auth's responsibility.


**TX08 — Guarded commands and truthful outcomes (ENG01).** Activation, initial selection/renewal, follow/unfollow and durable acquisition admission use TX01's database-owned auth fence, followed by actor/login binding and exact command-specific domain guards. Activation/selection keep their explicit final AuthReceiptV2 arguments and return server-only result/timing envelopes. Existing direct preference DML consumes the same trusted transaction-local receipt; raw client input cannot supply authority. Removing one's own follow requires no membership proof.

After the final guarded mutation decision, B either commits all domain state, required audit and required existing pending work, or rolls them all back. A **confirmed rollback** means no effects. An abort signal/transport error is not rollback proof. Unknown commit, or known commit followed by expired response lifetime, suppresses protected success and returns safe indeterminate. A later explicit fresh-auth retry reconciles the retained immutable command/proof identity; it does not duplicate a claim, reset selection or renew old evidence. Timing includes actual session/admission and applicable authority; D02 applies only to commands that require membership.

**Selected audit/rate adapter for new selection mutations.** Extend the existing `app_identity_audit_events.subject_type` constraint and existing audit-trigger owner with exactly `app_current_league_selections` and `app_league_renewals`. For a selection INSERT/UPDATE, subject_id is its stable league UUID, subject_user_id is derived through the exact association's app_user_id, and metadata is only its actual positive revision. For immutable renewal INSERT, subject_id is the renewal proof UUID, subject_user_id is derived through that proof's association, and metadata is `{}`. The active transaction-local actor must equal the resolved association owner for user commands; request_id is the trusted transaction-local command ID. Operators remain separately authorized under the existing audit actor rules. Do not accept a submitted actor/subject or infer ownership merely from a league UUID.

Both new event types use the **existing** shared per-actor mutation lock, ReadCommitted check and limit of 60 audited events per rolling 60 seconds, in the same mutation transaction. A renewal proof plus selection change emits and counts two events; a rejection of either event rolls back both records and all associated state. Existing subject branches and their event counting remain unchanged. Attach the new subject-aware triggers explicitly; unchanged six-subject triggers cannot cover these tables. The existing preference DELETE event is the canonical audit for its derived unfollow tombstone, with no extra counted tombstone event. Tombstones are writable only by that guarded trigger/owner path; direct account/runtime/target-command tombstone DML is forbidden. Audit or tombstone failure rolls back the preference change. Durable acquisition admission adds exactly one first-acceptance INSERT audit for app_acquisition_demands (subject_id demand ID, subject_user_id actual actor, metadata {}); idempotent replay/join adds none. The selected admission contract defines its atomic job handoff.

## Paper interleavings and arguments

These are completed design arguments under the stated participation/constraint assumptions. They are not executed SQL tests or evidence those assumptions hold in a deployed catalog.

| Schedule | Interleaving and selected outcome | Why |
| --- | --- | --- |
| PS01 Two actors claim one provider account | A and B hold different actor locks; A obtains account identity lock and commits; B then sees the claim and conflicts. If an insertion bypasses the precheck, active-account unique index rejects it. | Exactly one active claimant; transaction rollback also removes failed audit/link changes. |
| PS02 One actor claims two accounts of a provider | Both commands require the same actor lock; first commit makes second conflict with active(actor,provider). | Serial actor authority plus independent partial unique constraint. |
| PS03 Auth revocation during final read | Read holds shared auth gate/session row; revoke's exclusive gate waits. Read linearizes first, then revoke proceeds. If revoke committed first, live session check fails. | No allow combines pre-revocation session with later domain state; expiry is still checked at final clock. |
| PS04 Domain states that never coexisted | Reader locks actor/association before source connection; later mutations wait. The final snapshot sees the locked authority states together. If a needed mutation committed before the lock, reread sees its result. | Ordered stability, not a sequence of unrelated successful queries. Any timeout/abort emits no protected bytes. |
| PS05 New v1 removal during v2 promotion/read | Removal writer requires same connection UPDATE lock; it either commits before read's SHARE and appears in full evidence enumeration, or waits until after read's linearization. | Parent fence prevents an unenumerated phantom removal or newly qualified head from sneaking between checks. |
| PS06 Old positive after removal | P reserved at generation g; R commits at g+1; P arrives after R. P may not clear R, regardless of its local head ordinal. New P2 reserved after observing R can clear it only with independently qualified network proof and unchanged relevant authority. | Causal reservation receipt, not response arrival/version sorting. Unknown provider chronology remains labelled. |
| PS07 Acceptance crash | Crash before commit leaves neither accepted head nor new job; crash after commit leaves both. Worker retry reuses semantic job key/lease fences. | One existing-owner transaction and durable queue; no after-commit-only scheduling. |
| PS08 Renewal versus unfollow | Both lock actor/preference. Unfollow first yields larger tombstone revision, causing carryover rejection. Renewal first can retain only old following state; subsequent explicit unfollow removes it. | Either order ends with the newer explicit preference; no resurrection by stale transition. |
| PS09 A–B–A source identity | Attempt pins revision A1; mapping changes B2 then A3. A1 != A3 although native string is equal; acceptance/selection fails captured revision and authority checks. | Immutable revision identity and monotonic mapping generation. |
| PS10 Time expires after slow composition | Final trusted clock equals T+3600 while all non-time authority remains valid. Result denied; no retry/cached allow reuses T+3599. | Strict now < expiry, recomputed only at final decision; no timestamp refreshed by processing. |

Shared locks can increase contention and the auth gate serializes security mutations against short protected reads. That is an explicit correctness tradeoff for the first slice, not proof of capacity. Deadlock, lock timeout or connection failure yields indeterminate with no protected result; future optimization needs the same invariants and measured qualification.

Existing provision scripts explicitly reject extra privileged functions and unexpected auth tables. Therefore the future diff must update their **exact expected object/signature manifests**, not remove those rejection checks or replace them with a broad prefix allowlist. Function owners must be the verified migration-owned identities, never account/runtime/auth login roles. No permanent object CREATE, role inheritance, BYPASSRLS or blanket table permission is added. Helper bodies must reject unknown JSON fields, wrong actor/association/scope, stale revision, cross-audience references and arbitrary reader contract names.

## Method references

The design follows conceptual-to-logical-to-implementation separation from the [Open University database development lifecycle](https://www.open.edu/openlearn/science-maths-technology/the-database-development-life-cycle/content-section-1.5), with explicit functional-dependency and decomposition analysis using [Wilfrid Laurier University normalization notes](https://bohr.wlu.ca/cp363/notes/theory/09_normalization.php). PostgreSQL enforcement choices use the official documentation for [constraints](https://www.postgresql.org/docs/current/ddl-constraints.html), [transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html) and [security-definer function restrictions](https://www.postgresql.org/docs/current/sql-createfunction.html). Current online documentation is a design reference, not proof of the deployed PostgreSQL version or privileges.

Declared FD proofs and paper interleavings are finite design arguments. They do not certify actual catalog enforcement, provider behavior, capacity or a deployed system. Those empirical gates remain recorded in methodology and quality/operations documentation.

## Final adversarial admission corrections

Permit retry requires the immutable closed `requestContext`, not just `scopeHash`. It records the typed target/existing origin, tagged pre-enrollment/enrolled source and qualified resolved context/audience/mapping, with no auth material. Each source-backed retry reserves a new attempt in the same logical source scope and records its current lease. `responseObservedAt` records a once-only late unknown-to-observed HTTP refinement while preserving the original charge, deadlines and `completedAt`; late429 feedback counts at its actual observation and cannot accept late source data. Exact unions and helper algorithms are in [the admission contract](acquisition-admission-design.md); S19 mirrors them in the structural specification.

An existing transport `requestId` never returns another send-capable grant. Only the transaction inserting that permit may receive `granted`; uncertain commits dispatch nothing. `joined` admission means exact actor/command replay only. A distinct command ID colliding with unfinished semantic work is unaccepted/limited, preventing an unrecorded command alias from creating new work later. Shared source-job deduplication remains owned by the existing scheduler.
