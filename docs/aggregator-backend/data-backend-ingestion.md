This increment starts from production/main `87da4d0cb909ee280e125e73ad10e1c3dbd7cd9f`, on the separate `codex/data-backend-ingestion` branch. It follows [the data-only contract](data-backend-scope.md). **Data resource.** Explicit public username lookup, stable Sleeper user identity, associated leagues for one to three declared seasons, and selected leagues' official configuration, teams, observed primary/co-manager relationships, held-player membership and optional manager directory. A lookup proves what the public provider returned; it does not prove website ownership. Native IDs remain strings and season scope is explicit.

**Existing path.** `lib/sleeper.ts` owns the sole HTTP transport and existing discovery parsers. No page, new cron, queue, scorer, projection feed or website account participates.

**Persisted result.** The additive schema binds immutable identity observations to `league_source_manager_accounts`, season-list observations to exact intake/season keys, and each discovered candidate to its provider ID and season. Invalid discovery/bootstrap responses remain explicit retained rejection evidence. Candidate status and observation references advance under the existing job lease, generation, deadline and request revision. The canonical league/season/source, settings, team, manager and roster tables are reused. Data-only enrollment inserts `active=false` and does not alter existing flags or evidence; the existing registry excludes the new evidence literal using only an already-installed column. Canonical annual continuity is not inferred from username or roster numbers.

**Real evidence and gaps.** Offline composition tests exercise the real source parsers/normalizer and shared identity-writer composition with injected storage, including malformed scopes, unsupported analytics settings, independent directory failure, list restart, unknown completion acknowledgment, duplicate claim, expired fence and stored read isolation. These do not execute PostgreSQL. `integration/public-data-intake.integration-case.ts` is an **authored, unexecuted restricted-store/typed-readback oracle** using the maintained isolated harness and restricted runtime LOGIN. It manually advances retained fixture checkpoints under one job and tests admission separately; it is not full source→worker→PostgreSQL qualification. No SQL, provider request, credential lookup, migration, provisioning, activation, deployment or qualification workflow was performed. Independent frozen-source review and full offline verification are recorded separately in the review evidence.

Development validation: 138 tests passed across six intake, shared provider, worker, registry and normalizer files; zero failures/skips. ## Bounds, retry and compatibility

- Source selection is dormant. No existing route supplies the explicit backend intake selection. A backend operator must deliberately submit a stable UUID plus username/season window and select subsequent steps. Reusing that UUID with different input is rejected; resumption reads the stored next scope. A later refresh is a new explicit request, preserving prior observations. Operating automatic refresh/freshness has **not** been established.
- One identity/list/bootstrap/directory step makes at most one GET; a mapped core step makes at most three. Same-batch league evidence follows attempt reservation and supplies roster population proof. The runtime has a maximum 20-second step deadline and 25-second job lease. Database calls do not span HTTP. No implicit retry/redirect adds requests.
- The existing global job owner serializes intake work. Immutable dispatch admissions consume at least a 60-second interval even after failure or process death, across intake IDs. This is a public-intake bound, **not provider-wide qualification** of all legacy Sleeper callers. End-to-end latency and fleet throughput remain unmeasured.
- At most sixteen pending intake requests, three declared seasons/request, 1,000 source list rows/season and twenty selected candidate scopes/request are admitted. Remaining valid candidates are explicitly `capacity`. The existing sixteen-league enrollment ceiling remains; reservations share its advisory lock. A greater-than-twenty roster population is explicitly deferred as unqualified collection capacity, not declared intrinsically invalid official data. These are conservative existing-capacity boundaries, not format eligibility or measured scaling claims.
- Resource failure backs off from 60 seconds, with a maximum of five consecutive failures. Failed identity/list scopes terminate unavailable; failed candidates remain unavailable/partial, never completed-success. A partial core preserves its stored observations while the directory retries independently. Unavailable/partial readback retains resource reasons and timestamps. Reads never refresh acceptance or source timestamps.
- New source is compatible with installed 001–033 while dormant: unchanged callers do not read new tables; the registry filter uses existing `evidence`; the provisioning extension is conditional. This is an additive migration with no data rewrite or account cutover. Normal migration discovery will include 034, so its real SQL/catalog/grant review and authorized installation remain mandatory before selecting the new path.
- Keep dispatch generations, source evidence and collection reservations during recovery. Do not delete the shared job or release capacity blindly. Pausing selection stops new work and leaves accepted data readable. Rollback is source selection removal with the additive schema retained, not destructive schema/history removal. Orphan/reserved capacity, unknown commit recovery and concurrent fresh registration need actual isolated-SQL qualification before an operating release.

Completion of the full backend still requires the authorized live Sleeper identity/list acquisition and actual isolated PostgreSQL source→adapter→worker→stored-reader chain, restricted-role permissions, concurrency/rollback/crash tests, representative unrelated formats, full required resource coverage and measured freshness/recovery. Authored code and offline tests do not satisfy that completion boundary.
