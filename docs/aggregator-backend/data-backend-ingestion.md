## Bounds, retry and compatibility

- Source selection is dormant. No existing route supplies the explicit backend intake selection. A backend operator must deliberately submit a stable UUID plus username/season window and select subsequent steps. Reusing that UUID with different input is rejected; resumption reads the stored next scope. A later refresh is a new explicit request, preserving prior observations. Operating automatic refresh/freshness has **not** been established.
- One identity/list/bootstrap/directory step makes at most one GET; a mapped core step makes at most two. Core is checkpointed before the separately admitted directory step. Same-batch league evidence follows attempt reservation and supplies roster population proof. The runtime has a maximum 20-second step deadline and 25-second job lease. Database calls do not span HTTP. No implicit retry/redirect adds requests.
- The existing global job owner serializes intake work. Immutable dispatch admissions consume at least a 60-second interval even after failure or process death, across intake IDs. A dispatch is keyed by worker UUID and generation, so retained history survives the shared job's ordinary pruning/reset. Append-only outcomes distinguish committed checkpoints, failures and recovered interruption. Before dispatching, a new live owner resolves an unfinished prior admission and advances its exact revision once; an aborted old cleanup cannot leave unlimited zero-failure retries. This is a public-intake bound, **not provider-wide qualification** or the existing healthy current-period 60-second freshness target. End-to-end latency and fleet throughput remain unmeasured.
- At most sixteen pending intake requests, three declared seasons/request, 1,000 source list rows/season and twenty selected candidate scopes/request are admitted. Remaining valid candidates are explicitly `capacity`. The existing sixteen-league enrollment ceiling remains; DATA reservations and existing-consumer preparation share its advisory lock and combined capacity count. The same exact source may consume its own reservation. A greater-than-twenty roster population is explicitly deferred as unqualified collection capacity, not declared intrinsically invalid official data. These are conservative existing-capacity boundaries, not format eligibility or measured scaling claims.
- Resource failure backs off from 60 seconds, with a maximum of five consecutive failures. Failed identity/list scopes terminate unavailable; failed candidates remain unavailable/partial, never completed-success. A partial core preserves its stored observations while the directory retries independently. Unavailable/partial readback retains resource reasons and timestamps. Reads never refresh acceptance or source timestamps.
- Existing source paths remain compatible with installed 001–033: unchanged callers do not read new tables; the registry filter uses existing `evidence`; the provisioning extension is conditional. Migration034 additively replaces existing preparation to count DATA reservations and permit explicit inactive-DATA adoption; installed025 remains immutable and its activation guards stay unchanged. Normal migration discovery will include034, so real SQL/catalog/grant and existing-consumer qualification remain mandatory before installation.
- Registration rechecks its live owner after the capacity advisory lock and runs a bound postcondition after the existing identity statement in the same READ COMMITTED transaction. Failure rolls back that operation's identity and reservation changes. The shared helper preserves two returned rowsets and supports pinned savepoints. This is an assertion before transaction completion, not proof of deadline validity at a later caller-owned outer commit.
- Keep dispatch evidence and collection reservations during recovery. The shared job may undergo its ordinary retention lifecycle. Pausing selection stops new work and leaves accepted data readable. Rollback is source selection removal with the additive schema retained, not destructive schema/history removal. Orphan/reserved capacity, unknown commit recovery and concurrent fresh registration need actual isolated-SQL qualification before an operating release.
- Qualification harness cancellation is optional and backward compatible. Identity probes and cleanup check the signal before/after each query and owner acquisition; late continuations cannot begin the next reset statement. Pool/ownership release remains independent of that cancelled signal. An already-issued SQL operation has an unknown outcome until separately reconciled; abort checks do not prove server cancellation or rollback.

Completion of the full backend still requires the authorized live Sleeper identity/list acquisition and actual isolated PostgreSQL source→adapter→worker→stored-reader chain, restricted-role permissions, concurrency/rollback/crash tests, representative unrelated formats, full required resource coverage and measured freshness/recovery. Authored code and offline tests do not satisfy that completion boundary.
