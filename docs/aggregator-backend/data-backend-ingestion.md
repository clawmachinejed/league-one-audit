Immutable season-membership evidence remains unchanged. Both season-specific and default registry selection exclude unadopted DATA seasons, and installed activation still requires its original three fresh official heads. **Qualification boundary.** Offline composition tests use real parsers/normalization and injected storage; they are not SQL proof. The [resource and operating matrix](data-backend-evidence.md#resource-qualification-state) tracks current acceptance and remaining qualification for intake, live acquisition, interrupted-core/adoption, retained-generation recovery and wider fault/format/resource coverage. ## Bounds, retry and compatibility

- Source selection is dormant. No existing route supplies the explicit backend intake selection. A backend operator must deliberately submit a stable UUID plus username/season window and select subsequent steps. Reusing that UUID with different input is rejected; resumption reads the stored next scope. A later refresh is a new explicit request, preserving prior observations. Operating automatic refresh/freshness has **not** been established.
- One identity/list/bootstrap/directory step makes at most one GET; a mapped core step makes at most two. Core is checkpointed before the separately admitted directory step. Same-batch league evidence follows attempt reservation and supplies roster population proof. The runtime has a maximum 20-second step deadline and 25-second job lease. Database calls do not span HTTP. No implicit retry/redirect adds requests.
- The existing global job owner serializes intake work. Immutable dispatch admissions consume at least a 60-second interval even after failure or process death, across intake IDs. A dispatch is keyed by worker UUID and generation, so retained history survives the shared job's ordinary pruning/reset. Append-only outcomes distinguish committed checkpoints, failures and recovered interruption. Before dispatching, a new live owner resolves an unfinished prior admission and advances its exact revision once; an aborted old cleanup cannot leave unlimited zero-failure retries. This is a public-intake bound, **not provider-wide qualification** or the existing healthy current-period 60-second freshness target. End-to-end latency and fleet throughput remain unmeasured.
- At most sixteen pending intake requests, three declared seasons/request, 1,000 source list rows/season and twenty selected candidate scopes/request are admitted. Remaining valid candidates are explicitly `capacity`. The existing sixteen-league enrollment ceiling remains; DATA reservations and existing-consumer preparation share its advisory lock and combined capacity count. The same exact source may consume its own reservation. A greater-than-twenty roster population is explicitly deferred as unqualified collection capacity, not declared intrinsically invalid official data. These are conservative existing-capacity boundaries, not format eligibility or measured scaling claims.
- Resource failure backs off from 60 seconds, with a maximum of five consecutive failures. Failed identity/list scopes terminate unavailable; failed candidates remain unavailable/partial, never completed-success. A partial core preserves its stored observations while the directory retries independently. Unavailable/partial readback retains resource reasons and timestamps. Reads never refresh acceptance or source timestamps.
- Existing source paths remain compatible with installed 001–033: unchanged callers do not read new tables; the registry filter reads optional adoption authorization through `to_jsonb` so absent pre-034 columns fail closed; the provisioning extension is conditional. Migration034 additively replaces existing preparation to count DATA reservations and permit explicit inactive-DATA adoption; installed025 remains immutable and its activation guards stay unchanged. Normal migration discovery will include034, so real SQL/catalog/grant and existing-consumer qualification remain mandatory before installation.
- A current official scoring correction can provide roster population through its independently accepted settings receipt while the original immutable calculation profile and legacy scoring conflict remain. Additive034 replaces only the effective029 inner writer;030–033 wrappers remain. The alternate population check requires the current typed head, current source mapping, exact latest legacy scoring-conflict observation, and same-capture provenance/fence for supplied population. Equal-time source conflicts, remaps and newer pending settings attempts do not gain this exception.
- Registration rechecks its live owner after the capacity advisory lock and runs a bound postcondition after the existing identity statement in the same READ COMMITTED transaction. Failure rolls back that operation's identity and reservation changes. The shared helper preserves two returned rowsets and supports pinned savepoints. This is an assertion before transaction completion, not proof of deadline validity at a later caller-owned outer commit.
- Keep dispatch evidence and collection reservations during recovery. The shared job may undergo its ordinary retention lifecycle. Pausing selection stops new work and leaves accepted data readable. Rollback is source selection removal with the additive schema retained, not destructive schema/history removal. Orphan/reserved capacity, unknown commit recovery and concurrent fresh registration need actual isolated-SQL qualification before an operating release.
- Qualification harness cancellation is optional and backward compatible. Identity probes and cleanup check the signal before/after each query and owner acquisition; late continuations cannot begin the next reset statement. Pool/ownership release remains independent of that cancelled signal. An already-issued SQL operation has an unknown outcome until separately reconciled; abort checks do not prove server cancellation or rollback.

Live source → isolated PostgreSQL → stored-reader qualification is recorded only in the [evidence ledger](data-backend-evidence.md). Full backend completion requires every approved resource family and its integrity/operating evidence, including restricted-role and fault cases, real process death/restart, representative unrelated formats, measured freshness/capacity and recovery. Authored code, offline checks and selected SQL passes do not satisfy that wider completion boundary; consult the [resource and operating matrix](data-backend-evidence.md#resource-qualification-state) for current acceptance and remaining work.

R037 below removes the registration restriction on absent, null and empty settings/scoring/roster-slot fields. These source states were never inherently invalid official data. Its committed-bootstrap recovery, nine-state scoring/slot matrix and broader publication/migration compatibility have separate proof obligations in the [evidence ledger](data-backend-evidence.md#resource-qualification-state).

## R035: separately observed manager evidence

**Data resource.** Current provider-observed primary/co-manager fields for every team in the independently qualified roster population. Only an explicit null primary is a vacancy. An absent or malformed primary remains unknown with a distinct reason; a valid co-manager never becomes primary ownership or website authority. Valid co-manager IDs survive malformed siblings, duplicates and primary collisions with partial coverage; missing, null and malformed lists remain distinct unknown states. IDs retain provider spelling and source order.

**Existing path.** Backend callers opt in with `PublicIntakeSelection.managerEvidenceVersion: 'v2'` (or the corresponding injected coordinator dependency). The existing public Sleeper league and roster captures still make two GETs. Existing player and complete-primary v1 attempts and the settings attempt are preserved; one additional manager-evidence attempt is reserved before those requests. The sole administration normalizer adds the explicit v2 projection without changing the default v1 output, raw/semantic hashes or normalized legacy content. The existing atomic writer receives a sibling `teamManagerEvidenceAcceptance` argument. Changed-cache verification also reserves both existing v1 attempts plus the selected evidence attempt before its already-needed network verification.

**Persisted result.** Additive035 reuses canonical provider-manager identities, season teams, versioned manager entries/memberships and the existing typed resource scopes, receipts, acceptances and heads. The exact mapping, source observation, qualified league population, policy and attempt order remain required. Public intake supplies the same-capture league proof; existing changed-cache verification can reuse qualified count evidence only from an earlier accepted v2 receipt for the same mapping revision. V2 has its own acceptance identity and latest-evidence head, which may explicitly advance from complete to partial. Every response describes that one capture; no old primary or co-manager is carried forward. Immutable earlier evidence and the independent v1 complete-primary head remain intact. The effective034 population checks and030–033 wrappers remain in the writer chain. Existing callers keep their v1 two-attempt behavior and do not select v2.

**Backend read.** `readAcceptedTeamManagerEvidence(mapping)` revalidates stored raw fields, canonical memberships, version, mapping, coverage and receipt provenance. `readPublicSleeperIntake(client, administration, requestId, { managerEvidenceVersion: 'v2' })` exposes this result as `resources.teamManagerEvidence` with `captureBinding: 'latest-for-current-source-mapping'`. This is shared stored provider evidence, not a completion claim for that intake dispatch. When malformed primary evidence prevents v1 core completion, available partial v2 evidence remains readable, while the intake remains incomplete and v1 receipt-bound completion is unchanged. Exact receipt binding of v2 to a particular intake is not implemented or implied.

**Proof boundaries.** Offline tests reproduce the original malformed-primary loss; check explicit vacancy, absent/invalid fields, valid/malformed co-manager subsets, separate version/scopes, adverse reads without carry-forward, unchanged v1 hashes/readback, the same-request sibling producer/writer path and incomplete-intake readback. They use injected storage and do not qualify SQL atomicity or ordering. Additive035 and the authored real restricted-LOGIN manager-relationships oracle cover separate heads, replay, stale/out-of-order attempts, remapping, fences, immutable receipts and privilege denial. The [resource and operating matrix](data-backend-evidence.md#resource-qualification-state) records qualification of that dedicated oracle, intake/live v2 readback and operating selection/freshness separately. Intake readback of v2 evidence cannot qualify the dedicated oracle's full remap/ordering/permission matrix. The original R035 source-authoring increment made no DB connection, SQL execution, provider call, credential access, provisioning, migration application or activation.

## R036: durable recurring DATA selection

**Data resource.** Repeated acquisition of a configured stable Sleeper manager's identity, associated leagues for one to three declared seasons, and the same official core/directory resources as public intake. Recurrence does not add a new resource family, infer annual continuity, enroll a projection customer, or assert website ownership.

**Existing path.** The explicit backend `configurePublicSleeperRefresh` caller retains a bounded target using an existing identity-observation request. `runProductionProjectionSync({ publicDataRefresh: { enabled: true } })` starts one handled DATA promise before registry/projection loading. The `managerEvidenceVersion: 'v2'` sibling option remains explicit. No current route supplies this option; absent/force calls do not import the optional DATA runtime or query the recurrence schema. `runPublicDataRefreshStep` acquires the existing public-intake job once, atomically selects/binds an ordinary intake request, and then uses the existing recovery, next-step, admission, Sleeper captures, normalizer and writer. Manual intake remains on that same path. `readPublicDataRefresh` returns the stored target/current approval, scheduling and selection-failure fields, immutable current-cycle request/configuration, terminal outcome when observed, and the existing intake reader's resource receipts and coverage. It never contacts the provider.

**Persisted result.** Additive036 records an immutable configuration history, immutable target/cycle/request links, terminal cycle outcomes and exact-owner selection-failure history alongside a bounded target cursor. Stable provider identity is unique and cannot be changed by reconfiguration. At most sixteen target rows exist, including paused/expired targets; ordinary manual and recurring requests share the existing sixteen-pending-request ceiling. Configuration uses compare-and-swap revisions, explicit cadence from 60 seconds to seven days and an expiry no more than ninety days ahead. Seasons cannot change while the current request is nonterminal. Pause/resume or cadence/expiry changes preserve that request and its original cycle configuration while changing the current approval revision.

Only an actual durable dispatch admission advances `last_served_at`. Due selection orders by that field and scans at most sixteen targets; a separate selection-failure backoff of 60–3,600 seconds prevents a repeatedly failing pre-admission target from monopolizing selection. The exact worker/generation's stored selection and dispatch are reconciled before failure credit; busy ownership, admission throttle and setup/claim exhaustion before selection do not count as target failure. A selected target whose early database phase times out is reconciled under the original still-valid owner fence before a selection-failure backoff is recorded; a persisted admission takes precedence and receives no selection-failure credit. A new owner recovers an interrupted admitted step through the existing intake recovery. New terminal cycles retain new ordinary request IDs; previous evidence is never reset. A terminal outcome stores its next due slot once and skips missed cadence slots instead of creating a catch-up burst. A terminal or scheduling timestamp does not establish successful or fresh official content.

Admission rechecks current configuration revision, pause, expiry, cycle/request binding, source request revision and the existing owner/lease/deadline. An already-admitted capture may finish within its original fence after a pause. Unknown selection acknowledgments can recover the same persisted binding; they do not create another cycle. Restricted runtime grants expose only SELECT and the three narrow configure/select/failure APIs; the existing admission entry point retains its runtime grant and private delegates remain owner-only.

**Budget and compatibility.** Optional module loading is bounded by the original invocation start plus five seconds. The loading promise has immediate success/failure handlers; a late module resolution cannot start a worker. Only loading is bounded this way: live database/worker promises are fully awaited, never raced away. The actual abort-aware claim/selection/recovery/next/admission database client has an earlier absolute ten-second cutoff. Its independent reconciliation client gets at most two seconds, clipped to the original twenty-second work fence; the same job, worker and generation remain required. The provider/writer signal is independent of the early phase signal, so a successfully admitted capture can continue until the original twenty-second work deadline. Ordinary cleanup remains capped at plus twenty-two seconds. Imports, setup, selection and a delayed owner claim do not start a new budget. On normal projection completion, dispatch awaits the settled DATA promise and then calls ordinary administration maintenance exactly once using the original invocation timestamp and original failure handling. An outer `finally` drains DATA on registry/projection exceptions and early returns, preserving the original result or exception. One sanitized fixed-field warning records a rejected DATA setup/acquisition or unavailable outcome, including failures before durable target selection; logging failures cannot replace the projection outcome. This serializes those DATA and maintenance operations only within that invocation. Ordinary administration uses a different job key; cross-invocation overlap, provider-wide request budgets and sustained throughput still require real qualification. The public-intake admission interval remains sixty seconds and is not a fleet freshness guarantee.

**Proof boundaries.** Focused offline tests exercise the shared worker with real normalization, configuration/result validation, exact owner/unknown-ack handling, delayed claim/setup and cleanup budgets, stored reader scope/completeness, default/force isolation, registry/projection exceptions and preserved ordinary maintenance. Follow-up regressions reproduce six minute-spaced timeouts against one target and prove healthy-target progress after early-phase reconciliation; they exercise actual database AbortSignal forwarding, unselected exhaustion, committed admission with lost acknowledgment, provider-signal independence, a module loader held beyond twenty-two seconds, late-start suppression, and fully awaited already-started work. The [resource and operating matrix](data-backend-evidence.md#resource-qualification-state) and [source-bound SQL run history](data-backend-evidence.md#historical-sql-coverage-index) own SQL acceptance and remaining-case status for cycle/recovery, permission, pause/expiry, CAS, selection fairness, empty-list cycles, owner-history immutability, shared pending-request capacity, recurring exact-period metadata and paused-target capacity. These selected behaviors do not establish recurrence activation, sustained capacity/latency or operating freshness.
