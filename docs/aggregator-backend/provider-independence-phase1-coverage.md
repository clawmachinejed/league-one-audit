## Shared identity decision

Extend existing identity rows with namespace metadata and replace the affected source-key uniqueness with qualified uniqueness. Preserve canonical UUIDs and their foreign keys. Do not introduce parallel canonical identity tables, silently merge identities from equal display names, or place surrogate/fake values into native-ID columns to evade existing constraints.

The approved common mapping shape is:

- connectionId, leagueSeasonId, revisionId and generation;
- scope: provider, leagueKey, externalLeagueId, season and nativeNamespace;
- sourceNamespace: the mapping revision's existing season-context value.

scope.nativeNamespace is the provider's **league resource keyspace**. sourceNamespace is the revision's separate season context; existing 026 records use nfl:<season>. A manager account namespace or player catalog namespace is neither of these automatically. Team/player/manager references carry their own ProviderReference.nativeNamespace.

### Shared registration and lookup behavior

The first shared operation is registerCanonicalLeagueSeason(input, authorizedRegistration). Its input is {mode: 'official-data', leagueKey, leagueName, season, sourceLeague: ProviderReference, scoringRules?}; sourceLeague.resourceKind must be league. Scoring rules are not mandatory, and this increment does not establish calculation readiness. It returns the existing leagueId, leagueSeasonId and nullable scoringProfileId, together with CanonicalSourceMappingV1. Existing configured projection registration keeps its existing wrapper and immutable nonnullable-profile contract.

Here authorizedRegistration means {work, fence, registrationCapture}, not a caller assertion or serialized verified flag. The application method invokes **register_canonical_official_source(input jsonb, work jsonb, fence jsonb) RETURNS jsonb**. input contains the specified official-data registration fields and registrationCapture with its native source/version, origin, retained payload and versioned digest. The SECURITY DEFINER entry resolves the stored admitted work, registered source policy and actual fence, verifies the source/season identity and capture through its private adapter registration verifier, and checks ownership before and after the identity transaction. The return is the canonical IDs/profile/mapping described above. Existing production acquisition budgets and capacity limits remain.

Grant EXECUTE on this entry only to the existing restricted ingestion runtime; revoke it from PUBLIC and account/auth roles. Its owner is the non-runtime installation/function owner, with fixed search_path and schema-qualified objects. Private registration, namespace-policy, team and verifier helpers are not runtime-callable. Only the validated common flow may create a **nonlegacy** identity; a supplied key/name or native ID is not permission to attach to an existing league. Both current roles and scripts/provision-runtime-role.sql must encode these grants/denials.

Sleeper preserves the actual authority pattern in neon/public-intake.ts:294–344: queryAfterLock wraps registration with guard_public_data_intake(work, {...fence, reserveCollection: true}) before the write and guard_public_data_intake(work, fence) afterward (326–335), followed by checkpoint. Existing configured projection callers retain their legacy wrapper and permissions as specified below.

**Fixture bootstrap is explicitly different from Sleeper discovery.** public_data_league_candidates requires numeric IDs and Sleeper identity/list ancestry (034_public_data_intake.sql:37–54); an opaque fixture ID must not be forced through that native workflow. The isolated adapter uses an actual generic projection_jobs claim through the existing acquireJob method, with job_type = canonical-fixture-standings-v1 and a bounded fixture-only job key. Its immutable-for-the-attempt payload contains fixture policy/version, exact source league reference, intended canonical leagueKey and season, registration native digest and standings native digest. The source-pinned isolated policy enumerates the admitted fixture scopes and digest tuple; a matching caller label alone grants nothing. The test driver claims the job with its real restricted LOGIN; owner setup supplies only fixed policy/verifier branches, never league/team/accepted facts.

For this fixture branch, the common registration guard locks/checks the actual job row, state running, matching lease_owner, attempt_count/generation, unexpired lease and deadline, exact job type and payload/policy digest equality. It checks these again after waits and before commit. No public-data request, invented HTTP witness, Sleeper list or manager row is required or produced. The same common registration, attempt, writer, materializer and reader run afterward; the native admission mechanism is adapter-specific. Production policy rejects the fixture provider/job/origin. This proves the isolated common boundary, not Sleeper discovery or a real provider's authorization/network exchange.

The canonical resource reservation later generates its actual database nonce and binds this same job/fence, mapping and native digest tuple. Native fixture capture carries that DB-issued reservation evidence; an arbitrary nonce or a job reassigned to another source fails. Acquire/revalidate the real job before resource-head reservation in the documented lock order; when more than one lock is held, preserve the shared order: projection_jobs owner row → league-configuration advisory lock/source connection → resource head. Same-content evidence cannot substitute a different job, source, generation or nonce. These checks complement native equality; they do not claim cryptographic provider-origin authentication.

### First-slice permission and provider-policy closure

The existing runtime has SELECT/INSERT/UPDATE on leagues, league_seasons and league_source_connections (scripts/provision-runtime-role.sql:111–121). Preserve those legacy configured/Sleeper operations; do not revoke them indiscriminately. Existing enrollment, source-history and team tables are runtime SELECT-only (305–323) and remain so. Thus “no direct runtime writes” applies to new canonical evidence/materialization and protected team/enrollment tables, not to every pre-existing identity table.

Install guard_canonical_source_connection_identity on league_source_connections INSERT/UPDATE. It is SECURITY INVOKER, or an equivalently proven check of original execution context: a SECURITY DEFINER trigger checking its own current_user would incorrectly see the owner for direct runtime writes. The legacy runtime branch admits only provider sleeper with the exact documented legacy namespace and existing identity/CAS rules. Other providers/keyspaces require the non-runtime common registration owner context **and** the exact registered namespace/source policy. Work/capture/fence binding is enforced by the sole permitted owner entry before the mutation and rechecked before commit; it is not a caller-set GUC or boolean. A runtime role cannot SET ROLE to that owner. Audit all runtime-callable older SECURITY DEFINER functions that can mutate these tables; retain them only as exact Sleeper/nfl wrappers or deny EXECUTE so they cannot become a generic registration escape.

The existing literal provider CHECKs needing replacement in the first slice are league_administration_enrollments (016:5), league_administration_enrollment_seasons (016:21) and league_season_teams (016:171). Replace their sleeper-only restriction with CHECK(provider ~ '^[a-z][a-z0-9-]{0,63}$') plus nonbypassable policy/identity guards. Provider keys are deployment-controlled identifiers; this lexical form does not transform any native ID. Syntax alone is never admission. The new guards guard_canonical_enrollment_identity and guard_canonical_team_identity reject unknown provider, mismatched namespace/parent/source, or a nonlegacy write outside the owner entry. Validate parent source binding against the final transaction state, using a deferred constraint trigger where existing enrollment/connection insert order requires it; preserve the legacy ordering and immutability triggers. Do not change native administration-content, manager, catalog, draft or refresh-target provider CHECKs in this slice.

The private namespace/source policy has fixed deployment-owned branches: Sleeper's documented scopes in production, and explicitly enumerated isolated fixture scopes only in the source-pinned setup overlay. Fixture setup does not weaken table checks, ownership, grants or triggers. It modifies only the reviewed fixed policy/verifier branches. Both direct runtime INSERT and calls through older helpers must reject nonlegacy identities outside the guarded common entry. Reused native strings in different **admitted** namespaces must remain distinct; a namespace-policy mismatch must reject, not silently select another namespace.

The shared resolve-team helper remains private. Its newly created rows use the same source-policy/parent checks and existing immutable team protections. No direct runtime INSERT privilege is added. First-slice installation and qualification must inventory exact trigger/function definitions, current and subsequently provisioned-role grants, legacy CTE success, denied raw nonlegacy inserts, old-helper bypass attempts and rejected namespace-policy mismatches.

Reuse the current official-data registration behavior in projections/adapters/neon/identities.ts:26–71 and contracts.ts:38–55. Missing/null/empty scoring is retained as official data and does not require inventing a calculation profile. Preserve configured registration's immutable scoring rules. Generalize the literal Sleeper source identity at identities.ts:58–68 for the official-data common operation; preserve identities.ts:99–111 and existing configured callers through their explicit Sleeper compatibility wrapper.

The common registration entry resolves an existing identity by the exact qualified source tuple first and requires the expected season/canonical league to agree. For a new source tuple, intended leagueKey must match the admitted work/private policy; an already-used leagueKey cannot attach that source to an existing unrelated canonical league. Reject the collision. Existing Sleeper import key derivation remains sleeper-<externalLeagueId>; fixture keys are exact internal keys in the isolated policy/job payload. Do not infer cross-provider league equivalence from native strings or names. Explicit future identity linking is outside this first slice.

readSourceMapping currently accepts only an external league ID (store-contracts.ts:129; neon/administration.ts:164–180). The new method readCanonicalSourceMapping({sourceLeague: ProviderReference, leagueSeasonId?}) accepts only resourceKind league and returns the mapping shape above; when supplied, leagueSeasonId is an additional equality guard. Keep the old helper explicitly Sleeper/legacy-namespace scoped; do not search all providers or fall back to provider-only matching after a miss or ambiguity. A canonical lookup either finds exactly one correctly scoped identity, reports missing, or reports conflict; it never picks the first candidate.

The shared resolveCanonicalSeasonTeams({mapping, sourceLeague, sourceTeams}, verifiedCaptureContext) operation receives the authorized mapping, the verified source league reference and verified team ProviderReferences from the selected family capture. Its SQL materialization helper resolve_canonical_season_teams is private to the outer verified writer: PUBLIC, runtime and account/auth receive no EXECUTE. verifiedCaptureContext is constructed inside that writer only after registry dispatch, native/canonical equality and attempt/capture/mapping/fence validation. It binds the actual attempt, capture and qualified references; it is neither a caller-created boolean nor a reusable bearer authorization. It creates/resolves existing league_season_teams IDs inside the acceptance transaction, rejects duplicate references or conflicting associations, and returns source-reference → canonical UUID mappings. A caller cannot submit an arbitrary preaccepted team ID as proof. Corrected/replayed observations reuse the same qualified identity; remapping or equal labels do not silently transfer a canonical team.

Current standings SQL already creates team UUIDs independently of roster memberships (065_roster_provenance_contents.sql:594–599). Extract/reuse that responsibility under the common method; do not require a full roster or manager resource to manufacture identities. The full first-slice grant list remains in the shared/standings design: runtime receives no direct team/canonical-evidence table write, namespace initialization, registry modification or private inner-writer privilege; the explicit legacy identity DML allowance above remains.

Preserve guard_source_mapping_pointer, record_initial_source_mapping_revision, revise_league_source_connection and remap_league_source_connection ownership (026:68–167). New common variants bind namespace plus native ID in initial history, retries, current-pointer validation and CAS changes. Existing signatures remain explicit legacy wrappers. A change A → B → A is not an earlier exact retry, and old immutable reads retain their recorded mapping rather than being reassigned to the current connection.

## Minimum standalone standings dependency closure

The first slice needs a registered adapter/codec and authority policy; a real shared registration path for canonical league/season/source connection; mapped source/capture/attempt evidence; qualified team identities created through the shared method; and the common standings content, materialization and accepted reader specified by the companion designs.

Population proof may come from a correctly scoped independently evidenced league/settings count or another explicitly supported source population claim. Counting the returned rows is not independent proof that the set is complete. If population is unavailable or mismatched, retain the exact partial/unproved/mismatch state permitted by the standings contract; do not claim a full entity set.

It does **not** require manager ownership, players/membership arrays, a Sleeper player directory, linked scoring entities, a calculation profile, projection ingestion or a complete settings-family implementation. The official-data registrar already permits a null scoring profile; neon/enrollment.ts:25 still rejects it for the strict publication enrollment contract. Preserve that strict calculation/publication contract and use the shared official-data readiness policy for standings. Minimal identity or population facts are not a declaration that family 1 or 2 is fully implemented.

The synthetic source must travel through these real runtime-authorized methods. Owner-seeded team IDs, preaccepted rows, mocked SQL or hand-built final reader DTOs cannot demonstrate the complete path. Its standalone capture remains standings evidence, not a fabricated roster receipt.

## Reader and consumer boundary

Canonical selection is explicit: registered source, recorded common schema/version, family, exact SourceScope and requested current acceptance or immutable acceptance reference. It must validate the appropriate source mapping and receipt closure. An immutable historical selection uses its recorded revision; a current selection also applies the current mapping/head policy. A missing/unknown/corrupt canonical version cannot silently become a stale legacy success.

Legacy selection remains explicit by its recorded provider/codec/version and original receipt/content. Old records are not re-ingested, rehashed or stamped with current freshness. A compatibility codec may map exact stored facts into common semantics only under its reviewed version policy. Disabling new ingestion leaves valid accepted historical reads available according to the documented compatibility window.

No UI/route cutover is part of this design. Existing page-source.ts compatibility fallback, league and manager selection, browser polling, numeric presentation routes, cached payloads and League One/Two isolation remain unchanged. Numeric internal/display IDs may remain where their meaning is stable; an opaque external ID is never coerced to satisfy those routes. Future public navigation for a new provider is separate work.
