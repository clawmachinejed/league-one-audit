# Current screen provenance and proposed read contracts

Design inventory, 2026-09-28. Application evidence was inspected at `962d8708881c76a1bec9767cc659357b0206ad30`; current main and production at `92b8b0b` have the same application code and a documentation-only mission update. See the [verified baseline](README.md#baseline-and-scope). No provider calls, data changes, or application changes were made for this inventory. Proposed contract names below are design labels, not claims that these interfaces already exist.

## How to read this inventory

- **Official** means the host fantasy provider owns the fact (or the source fact behind a clearly identified derived display). **Sports** means the sports-data provider owns its supplied NFL metadata/statistics/game state. **League One** means our calculation, application preference, or explicitly curated correction.
- Source paths are repository-relative. Shared public payload types are in `apps/site/lib/types.ts`; callers and renderers must both be covered by migration tests.
- Every proposed read contract carries scope, source references, timestamps, completeness and feature availability as separate fields. One page-level `updatedAt` must not claim all constituent facts were observed together.
- Preserve existing outward routes and payloads with compatibility presenters while the canonical backend changes. Existing numeric roster IDs and Sleeper player strings are not suitable as new global canonical IDs.

The primary read-contract names for the design suite are `PortfolioSummary`, `LeagueOverview`, `MatchupDetail`, `TeamRoster`, `OfficialStandings`, `ProjectedStandings`, `ActivityFeed`, `ManagerDirectory`, `ManagerHistory`, `TeamSchedule`, and `AccountLibrary`. `LeagueOverview` supplies common identity, display metadata, current period and supported-feature context to league screens. The other names in the matrix denote constituent entities, field groups or assessments, not additional mandatory standalone services. Every reader envelope has per-field-group source references, availability, completeness, freshness, support and temporal context. Existing intentional presentation behavior is served by a v1 compatibility view; v2 unknown-state semantics are not silently adopted.

## Required canonical field categories beyond the visible cards

The screens depend indirectly on settings and source evidence. Collect these as bounded families, not as an unbounded promise to copy providers:

1. League season metadata, lifecycle, annual linkage, public name/artwork and visibility/access policy.
2. Team and manager identities, primary/co-owner relationships, effective attribution evidence and user preferences as separate families.
3. Roster slot definitions/eligibility; current roster groups; exact-period lineup/membership and official player/team points.
4. Fantasy matchups/schedule/results/finality and official standings; explicit source rank versus derived order.
5. Scoring dictionary and provenance, plus separately modeled competition/roster/transaction rules needed to interpret supported views.
6. Transactions, waiver state, bids/outcomes if exposed, pick/FAAB/player transfers; pagination/time-range completeness.
7. Player/team-defense metadata and crosswalk; NFL schedule/game-state and actual-stat observations; each sports-data source independent from fantasy host provider.
8. League One forecast/baseline/probability/metric result references with model/profile/calculation revisions; no provider projection silently labeled League One projection.
9. Observation/revision/completeness/freshness, accepted source connection, access grant, and reconciliation status per family.

Drafts, draft picks and playoff brackets are already captured as administration evidence (`apps/site/lib/sleeper.ts#getOfficialDraftAdministration/getOfficialAdministrationMetadata`, `league-administration`), but they do not currently have standalone user screens in this inventory. Draft-pick assets must remain available to transactions. Do not expand this phase into building a draft or bracket UX.

## Gaps and intentionally unresolved provenance

No entire current screen is unexplained after following its source loader, but several values have semantics that must be made explicit rather than copied into a generic `official` field:

- **Updated time is not consistently source time.** `getCore` uses page assembly time; `getRosterCore` uses calendar request completion; matchup data uses matchup request completion; snapshot `verifiedAt`, box-score `observedAt`, and metric cutoff are independent. A new contract must not claim a last-refreshed league timestamp verifies every subresource. Existing UI text requires a compatibility decision.
- **Rank is frequently locally computed.** Standings and current card rank use official totals sorted by local rules; Rosters uses a different local tiebreak. Source official rank is not established by those current paths. A provider that directly supplies rank should retain it, with its ranking system, separate from our optional derived order.
- **Roster PPG/rank is our calculation of actual statistics.** It is not equivalent to host-official scoring for arbitrary unsupported rules. It needs its own feature support and provenance, independent from projections and official scores.
- **Actual zero vs assumed zero.** `transform.ts#normalizeTeams` defaults absent W/L/T and PF parts to zero. The stricter Rosters reader separately checks source completeness. Proposed generic contracts should retain absence but keep a compatibility presenter until an intentional user-visible behavior change is approved.
- **Current metadata on historical views.** Names, teams and injury labels are not all historical facts; `Player.injuryStatus` explicitly documents current metadata. The new contract should carry `metadataAsOf`/temporal meaning rather than imply a historical snapshot of the player catalog.
- **History is inferred from verified provider links plus curated scope.** There is no guaranteed universal cross-provider permanent league lineage. Unknown lineage stays unknown; matching league names must never merge it.
- **No issues is not automatically verified clear.** The assessment already supports `unknown` coverage; the cross-league aggregate should require all expected lineups to be verified before claiming all are clear. This is a contract/acceptance criterion, not a fix made by this inventory.
- **Provider #2 parity is not proved by this inventory.** A Yahoo representative payload check must establish official team/player scores, scoreboard status, selected positions, ownership/authorization, pagination, and actually exposed transaction details. Any absent field gets `not_provided` or feature limitation, never an invented translation.

## Contract acceptance checklist

For each matrix row, the implementation package should record a fixture ID and assertion covering its normal, missing and unsupported cases. Shared acceptance gates:

- Existing exact-week and current-week route behavior is preserved; no cross-week substitution.
- Same team ID flows from account card into My Team and all detail reads; private grants scoped on every lookup/cache.
- Provider official total/adjustment survives normalization exactly; rounding is only presentation.
- Official detail remains available with no forecast, no probability, no roster metric and no projected standings.
- Absent lineups, true empty slots, absent bench, empty bench, and zero points stay distinct.
- Every rank, metric, probability and freshness label states whether it is sourced, calculated or curated.
- Profile, transaction and history links retain league/season/team scope; annual roster numbers never become permanent identity.
- Partial discovery, partial roster, partial transaction history and unsupported competition are explicit and isolated.
- Current catalog metadata does not become a false historical fact; verified game phase governs live/final behavior.
- Shared screens render provider-neutral contracts, with provider-specific wording limited to provenance/connection labels or explicit limitation messages.
