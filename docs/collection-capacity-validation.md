# Measured collection capacity

This report measures the collection implementation released in PR #251. It separates deterministic scheduler limits, isolated Neon timings and physical storage, and read-only observations of the current three-league production deployment. It does not enroll leagues or change application runtime, provider budgets, cron schedules, scoring, or the user interface.

## Reproducible measurements

- Run `node --conditions=react-server --import tsx scripts/measure-collection-scheduling-capacity.ts` from `apps/site` for the provider-free scheduling report. It runs the actual cadence and current admission policy for 3, 10, 20, 50, 100 and 300 leagues at Weeks 1, 3, 10 and 17, with separate preseason/default sensitivity cases.
- On Windows with Node 24, run `node --env-file=.env.integration.local --conditions=react-server --import tsx scripts/run-collection-capacity.mjs` from `apps/site` only under the existing isolated database safeguards, with `COLLECTION_CAPACITY_OUTPUT` pointing to a new absolute report path. This is a destructive disposable-database measurement. It must never target production or retained pilot accounts. The standard authorization, identity, sentinel, TLS, restricted-role and denylist gates apply before preparation and cleanup. The supervised runner must establish exclusive ownership of the disposable database before preparing it and hold that ownership through cleanup. Direct invocation of the capacity Vitest configuration is refused. Use `COLLECTION_CAPACITY_SCOPE=probe` for one three-league qualification capture, `ladder` (default) for the combined ladder and mixed-failure case, or `distinct` for a bounded distinct-profile extension. The extension does not repeat the mixed-failure qualification.
- The measured operation is the canonical all-player ingestion path and production Neon HTTP adapter, with synthetic provider replay. It preserves the 50-second work deadline, 55-second lease, eight concurrent league tasks, and eight-second league-source timeout. Each independent sample resets only its isolated job gate outside timing; it does not measure real polling frequency.

## Measurement contract

The adaptive database ladder is 3, 8, 16 and 32 leagues, with one shared profile and one profile per league. A first capture at each level, unchanged retrieval and correction distinguish content reuse from immutable history growth. The first level in each lane also retains a second capture that establishes history context before the unchanged assertion. Levels stop when results fail an invariant or retain less than ten seconds of work-budget headroom. A separate small cohort verifies slow-source, parity and registration failures without conflating isolation with overload.

The explicit synthetic workload has 4,385 scoring entities, complete starter and bench parity, and both 12-team/14-player and 10-team/20-player roster shapes. It deliberately exercises populated statistics and scoring breakdowns. It is not a captured NFL participation distribution. Official fixture values are generated by the shared calculator to construct a parity workload; independent scoring correctness remains covered by existing qualification tests.

Preserve every raw sample. SQL and stage durations can overlap; their sum is not operation elapsed time. Serialized SQL, parameter and decoded-result bytes are not wire traffic or billed Neon transfer. Physical heap/index/TOAST allocation can reuse existing pages and is not a universal marginal byte coefficient. The small, different capture samples do not establish p95/p99 or a service-level guarantee.

The distinct-profile extension completed seven more captures, all with correct acceptance and persistence. Three profiles took 22.81–28.73 seconds. Eight profiles took 38.55 seconds at first use, 31.12 seconds unchanged, and **41.35 seconds after a correction**. The final sample left **8.65 seconds** of the 50-second work budget, crossing the predeclared ten-second reserve. Expansion stopped there; **16 and 32 distinct profiles were not attempted**. Eight is neither a proven maximum nor a fleet-wide deployment recommendation. The combined evidence contains 26 correct captures across the main run and extension.

Eight distinct profiles produced 35,080 score rows for one 4,385-row changed capture, with 35.97 MiB of measured relation growth. The extension's peak sampled local RSS was 1,149 MiB, including fixtures and prior samples retained in the process. Scoring-profile diversity therefore costs substantially more than the same league count sharing rules.

The mixed cohort first established good results, then injected an 8.1-second source delay, an official-point mismatch and missing registration. The healthy league alone advanced; the two failed registered leagues retained their exact acceptance IDs, and the unregistered league never obtained a pointer. It created one new acceptance and 168 official-player observations. Shared data was collected once per operation and no live provider request was made.

### Storage and transport

At 32 leagues sharing rules, a changed capture added exactly 4,385 raw rows and 4,385 shared score rows, with 9,158,656 bytes (8.73 MiB) of measured relation allocation. An unchanged capture added zero raw or score rows, but still added 32 league acceptances and 5,888 official-player observations, with 1,097,728 bytes (1.05 MiB) of relation allocation. Verification history is retained even when score content is reused.

The same unchanged 32-league capture serialized about 18.42 MB of SQL parameters and decoded 4.84 MB of results. Three distinct profiles serialized about 39.55 MB of parameters on an unchanged capture despite zero raw/score row growth. Eight distinct profiles serialized 94.83 MB (90.43 MiB) of parameters per sample, including unchanged retrieval. Content deduplication therefore does not eliminate calculation, transport or verification work. The main run's maximum sampled local process RSS was 689 MiB; it includes Vitest, fixtures, retained reports and prior samples, and is not per-invocation Vercel memory.

Physical deltas cover the committed table allowlist including expected-game children, acceptance and pointer tables. They exclude WAL, restore history and unrelated tables. Do not multiply one dense synthetic correction by a season to infer production cost.

## Current production corroboration

Read-only evidence at application SHA `864580c67bae2380049c978346e3da076d5cdee5` found three enrolled leagues, 16 active watches each, no pending/failing watches, and no active worker leases. The production database occupied 916,037,632 bytes (873.6 MiB) at 2026-09-23 21:35 UTC; this is existing allocated storage, not a per-league coefficient or a full-season estimate.

A bounded visible Vercel log sample from 21:21–21:37 UTC contained 17 successful observer responses and 16 successful future-worker responses. Six active observer samples took 175–213 ms. Four active future samples each published one league in 5.82–6.77 seconds. Seventeen current-worker responses were successful with shared statistics not due. This quiet weekday sample does not establish live-game or larger-fleet capacity.

Both Neon endpoints were configured for 0.25–8 compute units. The measurement does not establish the instantaneous compute allocation or billed usage. No production load, provider requests, configuration changes, league enrollment or production writes were initiated by these tests.

## Qualification history

Retain the unsuccessful qualification attempts alongside the final measurements:

1. The first fixture used invented lowercase player IDs mixed with uppercase defense IDs. Acceptance rejected all three leagues. The diagnostic rerun found zero point mismatches but different JavaScript/PostgreSQL parity fingerprints because the IDs sorted differently. Numeric synthetic IDs matching Sleeper's identifier shape fixed the fixture; production code did not change. A fixture test now checks that ordering. Initial projection identities were also seeded before timing so the test measures an established catalog.
2. The corrected three-league probe passed all invariants in 22.497 seconds.
3. The first ladder stopped when its supposed unchanged capture wrote another raw content set. The first capture had established earliest player-team history, so the second capture legitimately had different history context. The final method retains a separate measured history-establishment capture before requiring steady-state content reuse; it does not suppress the extra storage or relax the unchanged-content assertion.

The first supervisor receipt recorded cleanup as unverified because it required zero backend sessions even after the child closed and schemas were empty. A fresh read showed only idle Neon HTTP connection-pool backends with no transaction, created during the owned test interval. Later supervisor checks permit only that narrowly attributed idle pool state and reject active transactions or unexplained sessions. No database sessions were terminated. Failed receipts are preserved rather than rewritten. The main run also needed the supervisor's guarded recovery cleanup after a teardown connection-close error; its final receipt proves the child closed, schemas were empty and remaining runtime pool sessions were idle with no transactions. The extension cleaned up normally.


## Engineering decisions and remaining work

1. **Complete:** bounded backend baseline measurement, shared-rule reuse, mixed league-failure isolation, physical storage accounting and current scheduler-policy replay. No application runtime, migration, provider configuration, cron, enrollment or production data changed.
2. **Next:** durable per-league continuation and fair retries against a stored shared capture. Keep work bounded per invocation so leagues with many distinct profiles do not need one increasingly long operation. Re-measure before increasing enrollment.
3. **Reduce repeated transfer and retained-history cost:** profile reuse saves rows but still sends substantial parameter payloads and adds official verification history. Measure a longer representative capture sequence before selecting retention or transport changes; this report authorizes no deletion or history rewrite.
4. **Resolve cadence capacity before broad onboarding:** the current 20-check allowance cannot meet the measured nominal demand at 20 leagues. Validate provider request budgets and fair backlog behavior before changing the allowance or refresh promises.
5. **Still unverified:** real live-provider latency/throttling, Vercel CPU/memory/cold starts, game-window contention, visitor concurrency, long-history query performance, full-season storage and billing. These remain explicit operational capacity gates; the synthetic backend baseline does not certify them.

## Boundaries

This measurement does not establish production visitor concurrency, Vercel CPU/cold-start behavior, live provider latency or throttling, whole-season storage/cost, or the absence of contention at kickoff. Larger-fleet promises require those operating conditions to be demonstrated. Durable per-league continuation/retry and queue fairness remain separate engineering capabilities; measurement can identify their need without implementing them.
